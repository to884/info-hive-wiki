# lint のワークフロー

wiki の健全性のチェックである。操作のたびにではなく、決まった頻度で（N 回の取り込みごと、毎週、またはユーザーが明示的に求めたときに）実行するのがよい。lint は、MCP のツール `lint`（または `wiki_lint.py`）が行う構造の確認と、LLM が直接行う内容の確認に分かれる。

コマンドの `<skill-root>` は、このスキルのディレクトリ（`SKILL.md` のあるディレクトリ）の実際のパスに置き換える。書き方は `SKILL.md` の「スクリプトのパス」にある。

## 手順 0: スキーマを確認する

`wiki/SCHEMA.md` で、この wiki 固有の追加の lint ルールが定義されていることがある（たとえば「エンティティのページにはすべて `aliases:` フィールドが必要」「ソースが2つ未満のコンセプトのページは作らない」）。これを読む。

## 手順 1: 構造の lint をかける

まず wiki の MCP サーバーのツール `lint` を使う。`wiki` に wiki のルートの絶対パスを渡す。`SCHEMA.md` がページの大きさの上限や必須の frontmatter を既定と違う値に決めている場合は、`soft_cap`、`hard_cap`、`soft_char_cap`、`hard_char_cap`、`required_fm` にその値を渡す。`SCHEMA.md` の「タグの体系」にタグが並んでいれば、そのタグをすべて `allowed_tags` に配列で渡す（CLI では `--allowed-tags` にカンマ区切りで渡す）。「構成の例」に挙げたタグも、この wiki で使っているなら含める。体系がひな形のまま空なら渡さない。渡さないとタグの検査はせず、`summary.unknown_tags` は `null`（0 ではない）になる。結果は下の CLI の `--json` と同じ形である。wiki に任意のグラフ層がある（`wiki/graph/ontology.yaml` がある）場合は、グラフの lint の結果も `graph.findings` に入る（`graph.state` が `checked`）。`disabled` はオントロジーがないこと、`error` はオントロジーを読めないことを表す。

ツールが使えないときは、スクリプトを実行する。使い分けは `SKILL.md` の「MCP のツールと CLI の使い分け」にある。

```bash
python "<skill-root>/scripts/wiki_lint.py" wiki/
```

`wiki/` は実際の wiki のディレクトリに置き換える。省くと、作業領域の設定（`.info-hive/workspace.json`）の `dirs.wiki`、設定がなければ `./wiki` を使う。設定が壊れているときは理由を書いて終了コード 1 で止まる。

グラフ層がある場合は、次も実行する。

```bash
uv run --script "<skill-root>/scripts/wiki_graph_lint.py" wiki/
```

グラフの lint は、構造の lint とは別に、型付きエッジの問題を検出する。対象は、未知の述語、証拠の欠落、リンク切れの目的語の参照、エイリアスの衝突、無効な `confidence`/`status` の値、リンク切れの `contradicts`/`supersedes` の参照である。検出結果は構造の lint と同じように仕分ける。つまり、修正案を示し、黙って適用しない。承認された修正を適用したら、extract で成果物を作り直す。手順、終了コード、オントロジーがないときの扱いの正本は `references/graph-workflow.md` である。

ユーザーが任意の判定レイヤーを有効にしている場合は、ツールではなく `wiki_graph_lint.py` を使い、`--decide` を付ける。証拠のテキストがソースページに出てこない型付きエッジをチェックする。矛盾を洗い出すには、`python "<skill-root>/scripts/wiki_decide.py" contradictions --wiki wiki/` を実行し、報告されたページの組を読んでから判断する。`decision-models.md` を参照。

lint が調べるページは、wiki の中の `.md` のうち、最上位の `SCHEMA.md`、`index.md`、`log.md`、`README.md` と、最上位の `indexes/`、`graph/`、`raw/`、`assets/`、`.evolution/`、`.wiki-cache/` の中のものと、名前が `.` で始まるファイルを除いたものである。検索（`wiki_search.py` と MCP の `query`）、統計、グラフも同じページを対象にする（`scripts/wiki_pages.py`）。

lint のレポートには、次のものが含まれる。

- **孤立ページ**: wiki のほかのどこからも wikilink で参照されていないページ。孤立ページは、たいてい、取り込みで親ページの更新を忘れたことを示す。インデックスを先に読むたどり方では見つけられないので、見えなくなる。
- **リンク切れの wikilink**: 存在しないページを指す `[[slug]]` の参照。たいていは、入力ミスか、参照元を更新せずに名前を変えたページである。ファイル名とリンク先は NFC にそろえてから比べるが、大文字と小文字は区別するので、`[[Kalman-Filter]]` は `kalman-filter.md` に解決しない。コードブロック（フェンスと字下げ）とインラインのコード（`` `[[例]]` ``）の中の `[[...]]` は、リンクとして数えない。記法の例を書くときは、コードに入れればリンク切れとして挙がらない。`\[\[例]]` のように角括弧を escape しても、リンクとして数える（閲覧で描く文字と同じ）。どこがコードかは、閲覧が使うものと同じ Markdown の解析器（同梱した markdown-it-py）で決める。
- **大きすぎるページ**: ハード上限（空白を除いて 25,000 文字、または 200 行）を超えるもの。ソフト上限（空白を除いて 10,000 文字、または 100 行）を超えるものは、分割を検討する大きいページとして別に挙がる。文字数は空白と改行を除いたコードポイントの数で、日本語も英語も 1 文字を 1 と数える。コードフェンス（mermaid の図を含む）の中身と、画像だけの行は、文字数にも行数にも数えない。上限は `--soft-char-cap`、`--hard-char-cap`、`--soft-cap`、`--hard-cap` で変えられる。
- **画像の参照先がない**（`missing_assets`）: 本文の `![説明](パス)` の参照先のファイルがないもの、または wiki の外を指すもの。参照先はページのファイルがあるディレクトリを基準に解決する。`wiki/<種類>/` のページから `wiki/assets/` の svg を `assets/...` と書いた場合は、正しい相対パス（`../assets/...`）を添えて指摘する。URL と、コードの中の画像の記法は見ない。
- **frontmatter の問題**: 必須のフィールド（既定では `type`、`title`、`tags`、`created`、`updated`。`--required-fm` で変えられる）がない、または YAML の形式が正しくないページ。
- **更新の止まったページ**: 被リンクが 3 つ以上あるのに、`updated:` の日付が 90 日より前のページ。よくリンクされるページは取り込みのたびに触れられるはずなので、スクリプトはこれで更新の止まったページを近似的に判定する。
- **重複したスラッグ**: 別々のサブディレクトリに、同じスラッグのページが2つあるもの（取り込みでの衝突が解消されていないことを示す）。Unicode の正規化（NFC と NFD）の違いだけで名前が異なるファイルも、重複として挙がる。
- **大文字と小文字だけが違うページかディレクトリ**（`case_only_duplicates`）: `concepts/Kalman.md` と `concepts/kalman.md`、`Concepts/` と `concepts/` のように、大文字と小文字を同一視すると同じになるパス。Windows と macOS の既定のファイルシステムでは同じ場所を取るので、閲覧のための書き出しで名前に接尾辞が付くか、書き出しが止まる。`kind` は、ページのファイルどうしなら `file`、ディレクトリの名前が違うなら `dir` である。どちらかの名前を変えるよう提案する。
- **索引の分類の誤り**（`index_type_mismatch`）: `index.md` の種類の見出し（「ソース」「エンティティ」「コンセプト」「シンセシス」と、英語の `Sources` など）の下に、別の `type` のページが並んでいるもの。たとえば「シンセシス」の欄にある `type: "source"` のページである。分割した索引（`indexes/sources.md`、`indexes/entities-people.md` など）は、ファイル名を種類として読む。読むのは見出しの下のリストの項目の最初の wikilink だけで、冒頭の説明文の例示や、要約の中のリンクは数えない。索引の項目がリンク切れのとき（分割した `index.md` が `indexes/` を指すときなど）と、`type` のないページは見ない。
- **出典の参照切れ**（`unresolved_sources`）: frontmatter の `sources:` に、ないページ（`reason` が `missing`）か、`type` が `source` でないページ（`not_source`）を書いているもの。`sources_consulted` は種類を問わないので見ない。
- **原本がない**（`missing_raw`）: source ページの `raw:` が指すファイルかディレクトリがないもの。相対パスは、wiki のルート（`../raw/...`、`../W1_Raw/...`）、wiki の親（取り込みのひな形の `raw/...`）、ページのディレクトリのどれかを基準にして見つかればよい。rag が書く `C:/...` のような絶対パスはそのまま確かめる。URL は見ない。
- **タグの体系にないタグ**（`unknown_tags`）: `allowed_tags`（`--allowed-tags`）を渡したときだけ、そこにないタグを持つページを挙げる。タグは NFKC にそろえてから比べる。
- **日本語の書き損じ**: 英語のキーと日本語の別名を両方書いている frontmatter（`title` と `タイトル` など）、キーのあとが全角の「：」になっている frontmatter、リストの値を「、」で区切っている frontmatter、全角の「｜」か「＃」を使った wikilink、`created`・`updated`・`ingested` の日付が `YYYY-MM-DD` の形になっていないページ、文字列の値が二重引用符で囲まれていない frontmatter（`unquoted_strings`。配列の要素も含む。日付と数値は対象外）。

このスクリプトは控えめに動く。検出結果を報告するが、修正はしない。レポートをユーザーに示す。

## 手順 2: 構造の検出結果を仕分ける

検出結果をユーザーと一緒に1件ずつ確認し、それぞれに修正案を示す。

- 孤立ページ: 適切な親ページからリンクする（こちらを優先する）か、そのページが本当に不要だと判断して削除する（まれである）。孤立ページが大量にたまっているなら、インデックスがおそらく古くなっている。インデックスの項目を作り直す。
- リンク切れ: 実際のページに合わせてリンクの名前を変えるか、あるべきページなら作成するか、そのコンセプトにページが要らないと分かったならリンクを削除する。
- 大きすぎるページ: 分割する。下位のコンセプトを独立したページに切り出し、親ページからリンクし、インデックスを更新する。
- frontmatter の問題: 欠けているフィールドを追加する。多くのページで同じ欠落があるなら、スキーマを緩めるべきか、初期化のテンプレートを改善すべきかを検討する。
- 更新の止まったページ: 最近更新された関連ページと、関係する raw ソースを読み、更新の止まったページの必要な箇所だけを更新する。
- 重複したスラッグ: 一方を正本とし、もう一方をそこにマージして削除する。名前のよいほうを正本に選び、被リンクは `grep` と `str_replace` で移し替える。
- 索引の分類の誤り: 項目を、ページの `type` に合う見出しの下（分割した索引なら、その種類のファイル）へ移す。ページの `type` のほうが誤っているなら、`type` とディレクトリを直す。
- 出典の参照切れ: 正しい source ページのスラッグに直すか、source ページがまだないなら取り込みを提案する。source でないページを参照したいなら、`sources_consulted` に移す。
- 原本がない: 原本を移したなら `raw:` のパスを直す。原本を失ったなら、ユーザーに確かめる。原本は raw の層にあり、lint の修正で作り直してはならない。
- タグの体系にないタグ: 体系にあるタグに置き換えるか、残す価値があるならユーザーと相談して `SCHEMA.md` の「タグの体系」に足す。
- 日本語の書き損じ: frontmatter のキーは英語に、コロンとリストの区切りは半角に、日付は `YYYY-MM-DD` の形に直す。wikilink の全角の「｜」「＃」は、区切りのつもりなら半角に直す。引用符のない文字列は、二重引用符で囲む。同じ wiki で多くのページに出るなら、まとめて直す提案をする。

修正案は、すでに行ったこととしてではなく、編集の提案として示す。承認するのはユーザーである。

## 手順 3: 内容の確認を行う

内容の確認は、スクリプトにはできない部分である。ページを読んで、内容について考える必要がある。ただし、wiki 全体を読む必要はない。内容に問題がありそうなページに絞る。

**最近更新されたページ。** 最後に変更された約 10 ページを読む（frontmatter の `updated:` かログで並べ替える）。次の点を探す。

- 同じトピックの古いページとの矛盾。新しい主張が古い主張を置き換えた場合は、古いほうに、置き換えられたことを注記する。両方が異なる文脈で正しい場合は、それぞれを明確にする。新しい取り込みが誤っていた場合は、元に戻す。
- ページ内部の矛盾（取り込みで新しい主張を重ねたのに、既存の文章とすり合わせていないもの）。
- まだ専用のページがないエンティティやコンセプトが、繰り返し言及されている。独立したページにする候補である。

**多くリンクされているページ（ハブ）。** 取り込みのたびに更新されるので、内容がもっともずれやすい。MCP のツール `stats` の `most_linked`（上位 10 件）か、`python "<skill-root>/scripts/wiki_search.py" "" --wiki wiki/ --top-linked 10` を実行する（または wikilink を grep して数える）と見つけられる。ハブをそれぞれ読み、文章の筋がまだ通っているか、相互参照がまだ意味をなしているかを確かめる。

**不確かさが明示されているページ。** 取り込みでは、言い切らずに留保を付ける（「ソースは X と主張しているが、まだ裏づけはない」）のが規約である。lint では、その後の取り込みで裏づけられたか、反証されたかを確かめ、それに応じて更新する。

## 手順 4: 足りない点を挙げる

参照されているのに、まだページになっていないものを探す。ツールの `lint` に `suggest_pages=true` を渡すか、次を実行する。

```bash
python "<skill-root>/scripts/wiki_lint.py" wiki/ --suggest-pages
```

多くのページ（既定では 5 ページ以上。`--suggest-min` で変えられる）に出てくるのに専用のページがない、エンティティやコンセプトらしい語を見つける。候補にするのは、3 文字以上のカタカナ語、3 文字以上の漢字の並び（「消費税」「仕入税額控除」など）、大文字で始まる英語の語句で、題名かスラッグが同じページがすでにあるものは除き、出てくるページの多い順に最大 30 件を挙げる。漢字の並びは途中で切らずに数えるので、「消費税率」は「消費税」とは別の語になる。どれを独立したページにし、どれを本文での言及のままにするかは、ユーザーが決められる。

まったく扱われていないものも探す。ユーザーが関心を示したのに、まだ取り込んでいないトピックである。ログが役に立つ（「3月に消費税のソースを5つ取り込んだが、それ以降は何もない。新しいソースを取り込みますか？」）。

## 手順 5: インデックスを更新する

lint の修正のあとは、ほぼ確実にインデックスの更新が必要になる。新しいページ、名前を変えたページ、削除したページ、変わった要約があるからである。影響を受けたインデックスの項目を、必要な箇所だけ作り直す。

`index.md` が 300 行を超えていて、まだ分割していないなら、分割するよい機会である。`scaling-playbook.md` を参照。

## 手順 6: ログに追記する

`## [YYYY-MM-DD] lint | 構造の修正 <N> 件、内容の修正 <M> 件、不足の提案 <K> 件` の形の行を1行追記する（`## [2026-11-03] lint | 構造の修正 3 件、内容の修正 1 件、不足の提案 2 件`）。操作名の `lint` は英語のまま書く。必要なら、影響の大きかった変更を並べたサブ行を加える。サブ行は 3 文字の空白で字下げし、日本語で書く。

## 頻度

妥当な既定は、構造の lint を5回の取り込みごと、内容の lint を毎週または 20 回の取り込みごと、足りない点の洗い出しを毎月である。ユーザーの作業のペースと、wiki の変化の激しさに合わせて調整する。急速に大きくなっている wiki ほど頻繁な lint が必要で、安定して成熟した wiki ではそれほど要らない。

ユーザーが明示的に lint を求めることもある（「wiki を整理して」「壊れているところは？」「lint をかけて」）。これは優先して扱う。ユーザーは何かに気づいたから頼んでいるのである。

## 避けるべきパターン

**黙って書き換える。** lint の検出結果は提案である。変更を承認するのはユーザーである。ユーザーの知らないうちに変わる wiki は、信頼できなくなる。

**lint を整理のためだけのものとして扱う。** 内容の確認は、新しいつながりを見いだす場でもある。10 ページを読んで、そのうち2つが根底にある同じ考えを指していると気づいたなら、それは lint の検出結果であるだけでなく、シンセシスのページの候補である。

**lint のレポートが手に負えなくなるまで放置する。** レポートが長すぎてユーザーが仕分けられないなら、頻度が合っていない（もっと頻繁にかける）か、wiki が規約に収まらないほど大きくなっている（スキーマを見直す）。

**問題がなさそうだからと lint をスキップする。** 気づかないうちに内容が壊れていくことは、もっとも検出しにくく、もっとも被害の大きい失敗である。lint はそれを見つける。
