# lint のワークフロー

wiki の健全性のチェックである。操作のたびにではなく、決まった頻度で（N 回の取り込みごと、毎週、またはユーザーが明示的に求めたときに）実行するのがよい。lint は、`wiki_lint.py` が行う構造の確認と、LLM が直接行う内容の確認に分かれる。

## 手順 0: スキーマを確認する

`wiki/SCHEMA.md` で、この wiki 固有の追加の lint ルールが定義されていることがある（たとえば「エンティティのページにはすべて `aliases:` フィールドが必要」「ソースが2つ未満のコンセプトのページは作らない」）。これを読む。

## 手順 1: 構造の lint スクリプトを実行する

```bash
python scripts/wiki_lint.py wiki/
```

wiki に任意のグラフ層がある（`wiki/graph/ontology.yaml` がある）場合は、次も実行する。

```bash
uv run --script scripts/wiki_graph_lint.py wiki/
```

このスクリプトは、構造の lint とは別に、型付きエッジの問題を検出する。対象は、未知の述語、証拠の欠落、リンク切れの目的語の参照、エイリアスの衝突、無効な `confidence`/`status` の値、リンク切れの `contradicts`/`supersedes` の参照である。検出結果は構造の lint と同じように仕分ける。つまり、修正案を示し、黙って適用しない。承認された修正を適用したら、`uv run --script scripts/wiki_graph_extract.py wiki/` を実行して、コンパイル済みの成果物を更新する。

ユーザーが任意の判定レイヤーを有効にしている場合は、`wiki_graph_lint.py` に `--decide` を付ける。証拠のテキストがソースページに出てこない型付きエッジをチェックする。矛盾を洗い出すには、`python scripts/wiki_decide.py contradictions --wiki wiki/` を実行し、報告されたページの組を読んでから判断する。`decision-models.md` を参照。

lint のレポートには、次のものが含まれる。

- **孤立ページ**: wiki のほかのどこからも wikilink で参照されていないページ。孤立ページは、たいてい、取り込みで親ページの更新を忘れたことを示す。インデックスを先に読むたどり方では見つけられないので、見えなくなる。
- **リンク切れの wikilink**: 存在しないページを指す `[[slug]]` の参照。たいていは、入力ミスか、参照元を更新せずに名前を変えたページである。ファイル名とリンク先は NFC にそろえてから比べるが、大文字と小文字は区別するので、`[[Kalman-Filter]]` は `kalman-filter.md` に解決しない。
- **大きすぎるページ**: ハード上限（空白を除いて 25,000 文字、または 200 行）を超えるもの。ソフト上限（空白を除いて 10,000 文字、または 100 行）を超えるものは、分割を検討する大きいページとして別に挙がる。文字数は空白と改行を除いたコードポイントの数で、日本語も英語も 1 文字を 1 と数える。コードフェンス（mermaid の図を含む）の中身と、画像だけの行は、文字数にも行数にも数えない。上限は `--soft-char-cap`、`--hard-char-cap`、`--soft-cap`、`--hard-cap` で変えられる。
- **画像の参照先がない**（`missing_assets`）: 本文の `![説明](パス)` の参照先のファイルがないもの、または wiki の外を指すもの。参照先はページのファイルがあるディレクトリを基準に解決する。`wiki/<種類>/` のページから `wiki/assets/` の svg を `assets/...` と書いた場合は、正しい相対パス（`../assets/...`）を添えて指摘する。URL と、コードの中の画像の記法は見ない。
- **frontmatter の問題**: 必須のフィールド（既定では `type`、`title`、`tags`、`created`、`updated`。`--required-fm` で変えられる）がない、または YAML の形式が正しくないページ。
- **更新の止まったページ**: 被リンクが 3 つ以上あるのに、`updated:` の日付が 90 日より前のページ。よくリンクされるページは取り込みのたびに触れられるはずなので、スクリプトはこれで更新の止まったページを近似的に判定する。
- **重複したスラッグ**: 別々のサブディレクトリに、同じスラッグのページが2つあるもの（取り込みでの衝突が解消されていないことを示す）。Unicode の正規化（NFC と NFD）の違いだけで名前が異なるファイルも、重複として挙がる。
- **日本語の書き損じ**: 英語のキーと日本語の別名を両方書いている frontmatter（`title` と `タイトル` など）、キーのあとが全角の「：」になっている frontmatter、リストの値を「、」で区切っている frontmatter、全角の「｜」か「＃」を使った wikilink、`created`・`updated`・`ingested` の日付が `YYYY-MM-DD` の形になっていないページ、文字列の値が二重引用符で囲まれていない frontmatter（`unquoted_strings`。配列の要素も含む。日付と数値は対象外）。

このスクリプトは控えめに動く。検出結果を報告するが、修正はしない。レポートをユーザーに示す。

## 手順 2: 構造の検出結果を仕分ける

検出結果をユーザーと一緒に1件ずつ確認し、それぞれに修正案を示す。

- 孤立ページ: 適切な親ページからリンクする（こちらを優先する）か、そのページが本当に不要だと判断して削除する（まれである）。孤立ページが大量にたまっているなら、インデックスがおそらく古くなっている。インデックスの項目を作り直す。
- リンク切れ: 実際のページに合わせてリンクの名前を変えるか、あるべきページなら作成するか、そのコンセプトにページが要らないと分かったならリンクを削除する。
- 大きすぎるページ: 分割する。下位のコンセプトを独立したページに切り出し、親ページからリンクし、インデックスを更新する。
- frontmatter の問題: 欠けているフィールドを追加する。多くのページで同じ欠落があるなら、スキーマを緩めるべきか、初期化のテンプレートを改善すべきかを検討する。
- 更新の止まったページ: 最近更新された関連ページと、関係する raw ソースを読み、更新の止まったページの必要な箇所だけを更新する。
- 重複したスラッグ: 一方を正本とし、もう一方をそこにマージして削除する。名前のよいほうを正本に選び、被リンクは `grep` と `str_replace` で移し替える。
- 日本語の書き損じ: frontmatter のキーは英語に、コロンとリストの区切りは半角に、日付は `YYYY-MM-DD` の形に直す。wikilink の全角の「｜」「＃」は、区切りのつもりなら半角に直す。引用符のない文字列は、二重引用符で囲む。同じ wiki で多くのページに出るなら、まとめて直す提案をする。

修正案は、すでに行ったこととしてではなく、編集の提案として示す。承認するのはユーザーである。

## 手順 3: 内容の確認を行う

内容の確認は、スクリプトにはできない部分である。ページを読んで、内容について考える必要がある。ただし、wiki 全体を読む必要はない。内容に問題がありそうなページに絞る。

**最近更新されたページ。** 最後に変更された約 10 ページを読む（frontmatter の `updated:` かログで並べ替える）。次の点を探す。

- 同じトピックの古いページとの矛盾。新しい主張が古い主張を置き換えた場合は、古いほうに、置き換えられたことを注記する。両方が異なる文脈で正しい場合は、それぞれを明確にする。新しい取り込みが誤っていた場合は、元に戻す。
- ページ内部の矛盾（取り込みで新しい主張を重ねたのに、既存の文章とすり合わせていないもの）。
- まだ専用のページがないエンティティやコンセプトが、繰り返し言及されている。独立したページにする候補である。

**多くリンクされているページ（ハブ）。** 取り込みのたびに更新されるので、内容がもっともずれやすい。`wiki_search.py --top-linked 10` を使う（または wikilink を grep して数える）と見つけられる。ハブをそれぞれ読み、文章の筋がまだ通っているか、相互参照がまだ意味をなしているかを確かめる。

**不確かさが明示されているページ。** 取り込みでは、言い切らずに留保を付ける（「ソースは X と主張しているが、まだ裏づけはない」）のが規約である。lint では、その後の取り込みで裏づけられたか、反証されたかを確かめ、それに応じて更新する。

## 手順 4: 足りない点を挙げる

参照されているのに、まだページになっていないものを探す。次を実行する。

```bash
python scripts/wiki_lint.py wiki/ --suggest-pages
```

多くのページ（既定では 5 ページ以上。`--suggest-min` で変えられる）に出てくるのに専用のページがない、エンティティやコンセプトらしい語を見つける。候補にするのは、3 文字以上のカタカナ語、3 文字以上の漢字の並び（「消費税」「仕入税額控除」など）、大文字で始まる英語の語句で、題名かスラッグが同じページがすでにあるものは除き、出てくるページの多い順に最大 30 件を挙げる。漢字の並びは途中で切らずに数えるので、「消費税率」は「消費税」とは別の語になる。どれを独立したページにし、どれを本文での言及のままにするかは、ユーザーが決められる。

まったく扱われていないものも探す。ユーザーが関心を示したのに、まだ取り込んでいないトピックである。ログが役に立つ（「3月に消費税のソースを5つ取り込んだが、それ以降は何もない。新しいソースを取り込みますか？」）。

## 手順 5: インデックスを更新する

lint の修正のあとは、ほぼ確実にインデックスの更新が必要になる。新しいページ、名前を変えたページ、削除したページ、変わった要約があるからである。影響を受けたインデックスの項目を、必要な箇所だけ作り直す。

`index.md` が 300 行を超えていて、まだ分割していないなら、分割するよい機会である。`scaling-playbook.md` を参照。

## 手順 6: ログに追記する

`## [YYYY-MM-DD] lint | 構造の修正 <N> 件、内容の修正 <M> 件、不足の提案 <K> 件` の形の行を1行追記する（`## [2026-11-03] lint | 構造の修正 3 件、内容の修正 1 件、不足の提案 2 件`）。操作名の `lint` は英語のまま書く。必要なら、影響の大きかった変更を並べたサブ行を加える。サブ行は 3 文字の空白で字下げし、日本語で書く。

## 頻度

妥当な既定は、構造の lint を5回の取り込みごと、内容の lint を毎週または 20 回の取り込みごと、足りない点の洗い出しを毎月である。ユーザーの作業のペースと、wiki の変化の激しさに合わせて調整する。急速に大きくなっている wiki ほど頻繁な lint が必要で、安定して成熟した wiki ではそれほど要らない。

ユーザーが明示的に lint を求めることもある（「wiki を整理して」「壊れているところは？」「lint をかけて」）。これは優先して扱う。ユーザーは何かに気づいたから頼んでいるのである。

## 避けるべきパターン

**黙って書き換える。** lint の検出結果は提案である。変更を承認するのはユーザーである。ユーザーの知らないうちに変わる wiki は、信頼できなくなる。

**lint を整理のためだけのものとして扱う。** 内容の確認は、新しいつながりを見いだす場でもある。10 ページを読んで、そのうち2つが根底にある同じ考えを指していると気づいたなら、それは lint の検出結果であるだけでなく、シンセシスのページの候補である。

**lint のレポートが手に負えなくなるまで放置する。** レポートが長すぎてユーザーが仕分けられないなら、頻度が合っていない（もっと頻繁にかける）か、wiki が規約に収まらないほど大きくなっている（スキーマを見直す）。

**問題がなさそうだからと lint をスキップする。** 気づかないうちに内容が壊れていくことは、もっとも検出しにくく、もっとも被害の大きい失敗である。lint はそれを見つける。
