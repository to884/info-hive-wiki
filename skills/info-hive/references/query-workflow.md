# クエリのワークフロー

ユーザーが wiki に対して質問している。やるべきことは、wiki をもとに出典つきで答え、wiki の規模に応じてたどり方を変え、必要なら回答をシンセシスのページとして保存することである。

コマンドの `<skill-root>` は、このスキルのディレクトリ（`SKILL.md` のあるディレクトリ）の実際のパスに置き換える。書き方は `SKILL.md` の「スクリプトのパス」にある。

## 手順 0: スキーマを確認する

このセッションでまだ読んでいなければ、`wiki/SCHEMA.md` を読む。wiki によっては、クエリ専用の規約を定めている（たとえば「比較を問う質問には、必ず比較表で答える」「回答は `wiki/synthesis/` ではなく `wiki/synthesis/qa/` に置く」）。スキーマは既定の動作より優先される。

## 手順 1: インデックスを読む

必ず `wiki/index.md` から始める。インデックスが `wiki/indexes/` に分割されている場合は、先にトップレベルの `index.md` を読んで、どの分割されたインデックスが関係するかを見つけ、それを読む。

インデックスは、まさにこのために作ってある。1ページにつき1行で、短い要約が付いている。たいていの場合、インデックスだけで候補のページを見つけられるはずである。クエリが複数の分割されたインデックスにまたがる場合（たとえば「論文 A と B の方法論を比べて」）は、関係するものをすべて読む。

## 手順 2: 候補のページを絞り込む

インデックスから、クエリに関係しそうなページの短い一覧を作る。厳選すること。1つの質問に答えるために 30 ページも読むなら、力任せの検索に戻ってしまっている兆候であり、それではスケールしない。インデックスの要約で候補を見分けにくい場合は、インデックスの項目が簡潔すぎるという兆候である。次の lint のときのために記録しておく。

インデックスからよい候補が見つからない場合（クエリがあいまいな言葉や分野特有の言葉を使っていて、インデックスの要約と一致しない場合）は、検索を使う。

まず wiki の MCP サーバーのツール `query` を使う。`wiki` に wiki のルートの絶対パス、`query` に検索語を渡す（`top`、`type`、`tags`、`since`、`per_page` で絞り込める）。結果の形は下の CLI の `--json` と同じで、セクション単位のハイブリッド検索の結果が返る。サーバーの埋め込みは cl-nagoya/ruri-v3-130m の ONNX、ベクトル索引は usearch、語彙検索は Tantivy で、索引は wiki の外に置く（`mcp-server.md`）。埋め込みモデルを用意している途中か使えないとき、または索引を埋め込んでいる途中は、結果の `warning` に理由が入る。埋め込みの途中は `index.state` が `embedding` になる。どのときも語彙検索は wiki 全体を対象にするので、結果をそのまま使い、意味の検索を使えなかったか一部だけだったことを回答に添える（手順 5b の「検索の縮退」）。ツールが結果を返したら、0 件でも、同じ検索を CLI でやり直さない。

ツールが使えないとき、呼び出しが返らないとき、ページ単位の順位（`--granularity page`）や依存パッケージを使わない決定的な検索が要るときは、検索スクリプトを使う。使い分けは `SKILL.md` の「MCP のツールと CLI の使い分け」にある。

```bash
uv run --script "<skill-root>/scripts/wiki_search.py" "軽減税率の対象" --top 10 --cache --json
```

`--wiki` を省くと、作業領域の設定（`.info-hive/workspace.json`）の `dirs.wiki`、設定がなければ `./wiki` を検索する。設定が壊れているときは理由を書いて終了コード 1 で止まる。

スクリプトも、既定では、セクション単位のハイブリッド検索の結果を返す。ローカルの FastEmbed によるセマンティックな順位付けと BM25 を RRF で統合し、JSON の各行には `heading_path`、抜粋、検索の出所が付く。埋め込みモデルの既定は多言語モデルの `intfloat/multilingual-e5-small`（fp16 の ONNX、約 0.25 GB、384 次元）で、初回のセマンティック検索でダウンロードする。環境変数 `INFO_HIVE_EMBED_MODEL` で `intfloat/multilingual-e5-large`（約 2.24 GB、1024 次元）も選べ、モデルを変えるとベクトルの索引は自動で作り直される。セクションのベクトルは `wiki/.wiki-cache/embeddings.sqlite` に保存され、変更されたセクションだけがベクトル化し直される。wiki やクエリのテキストがマシンの外に出ることはない。依存パッケージを使わない語彙ベースの BM25 にしたい場合は、`python "<skill-root>/scripts/wiki_search.py" "軽減税率の対象" --no-embed` を実行する。必要に応じて frontmatter のフィルター（`--type concept`、`--tag 税制`、`--since 2026-01-01`）を使い、ページ単位の語彙ベースの順位付けにしたいときは `--granularity page` を指定する。

日本語のクエリはそのまま渡してよく、分かち書きは要らない。語彙ベースの検索は、かなと漢字を 2 文字ずつ重ねて切り出し（文字 bigram）、漢字は 1 文字単位でも索引に入れるので、「税」のような単漢字のクエリも「消費税」を含むページに当たる。形態素解析は使わない。文字 bigram は偶然に一致しやすいので、日本語を含むクエリでは、クエリのトークンの被覆率（IDF で重み付け）が 0.25 未満のページを語彙ベースの結果から外す。詳しくは、リポジトリの `docs/search.md` を参照。

ユーザーが任意の判定レイヤーを有効にしている場合は、ツールではなく検索スクリプトを使い、`--decide` を付ける。このふるい分けは、クエリと単語が共通しているだけの行を取り除く。ふるい分けた結果が空なら、wiki にはおそらく答えがない。結果が `failed_open: true` を報告している場合は、ふるい分けが実行されていない。`decision-models.md` を参照。

## 手順 2b: グラフを使って調べる（`wiki/graph/ontology.yaml` がある場合のみ）

関係を問う質問（「X とつながっているものは？」「Y を提案したのは誰？」「A から B への経路をたどって」）では、インデックスを読んだあと、ページを読む前に、コンパイル済みのグラフに問い合わせる。手順と鮮度の確かめ方は `references/graph-workflow.md` の「問い合わせ（query）」に従う。

構造化された隣接ノードや事実は、読むべき wiki ページを選ぶのに使う。重要な主張については、グラフの行だけをもとに答えてはならない。証拠になるのは wiki ページとその raw ソースである。`ontology.yaml` がない wiki では、`graph.sqlite` が残っていてもこの手順を飛ばす。

## 手順 3: 候補のページを読む

候補のページをそれぞれ全文読む。読みながら、関係しそうなほかのページへの wikilink を控えておく。それらは、あらかじめ整理された手がかりである。見込みのありそうなものはたどるが、すべてのリンクを再帰的に追いかけてはならない。そうすると、あまり関係のないページでコンテキストウィンドウを使い果たしてしまう。

あるページが frontmatter でソースの要約ページを参照していて、答えがそのソースの実際の記述にかかっている場合は、ソースの要約ページも読む。wiki の要約で明らかに足りない場合を除き、raw ソースまで戻ることは避ける。統合はすでに済んでいるというのが、wiki の要点だからである。

## 手順 4: 必要なら被リンクを探す

クエリが「X について wiki には何が書いてある？」や「X はどこで言及されている？」で、X に専用のページがある場合は、そのページ自体よりも、そこへの被リンクのほうが興味深いことが多い。付属の `wiki_search.py` の `--backlinks` で見つける。MCP のツールにはこの機能がない。

```bash
python "<skill-root>/scripts/wiki_search.py" "" --wiki "<absolute-wiki-root>" --backlinks <page-slug>
```

ページを読んで言及を探すより速く、`[[slug|表示名]]` や `[[dir/slug]]` の形のリンクも数える。結果は見つけた順に並び、関係の深さの順ではない。`grep -rl "\[\[<page-slug>\]\]"` はこれらの形を拾わないので、使わない。

## 手順 5: 回答をまとめる

回答は自分の言葉で書き、使った wiki ページへの `[[wikilink]]` を出典として付ける。役に立つ場合は、特定の raw ソースを `raw/<file>` で参照する。出典は重要である。ユーザーは出典を使って回答を検証し、さらに調べられる。

wiki に矛盾する主張がある場合は、どちらか一方を選んで確定したことのように示さず、矛盾をそのまま示す。wiki の価値の一部は、分かっていることと議論が分かれていることを区別して追跡できる点にある。

wiki にクエリに関係する内容がない場合は、そうはっきり伝える。話をでっち上げてはならない。でっち上げた回答が保存されると、それが wiki を汚すもっとも確実な原因になる。代わりに、足りない部分を補うためにユーザーが取り込めるソースを提案する。

## 手順 5b: 確からしさ（confidence）を付ける

回答の終わりに、回答の確からしさを「高」「中」「低」の 3 段階で示し、そう決めた理由を添える。確からしさは、wiki がその回答をどれだけ裏づけているかを表す。答えが世の中で正しい確率ではない。回答の正誤を確かめた評価のデータはないので、パーセントや 0.8 のような数値にしてはならない。

判定するのは、回答の結論（質問への答えそのもの）と、結論を導くのに使ったすべての前提である。結論が変わらない補足は判定しない。前提は結論が頼った主張で、wiki から取ったものも、wiki の外の知識で補ったものも含む。結論は前提をそのまま述べたものか、前提から導いたものである。

決め方は次の 3 段である。順番や読み手の印象で変わらないように、上げる方向の要因は設けない。

1. 前提ごとに、どこに書かれていたかで出発点を決める（「前提の出発点」）。
2. 前提ごとに上限を当て、出発点と上限のうち低いほうを、その前提の確からしさにする（「上限」）。
3. 結論の確からしさを、前提の確からしさと導き方で決める（「結論の導き方」）。結論にも上限を当てる。

回答全体の確からしさは、結論と前提のうちもっとも低いものにする。質問に複数の結論で答え、結論によって確からしさが違うときは、それぞれの結論のそばに「（確からしさ: 高）」「（確からしさ: 低）」のように書く。

wiki に関係する内容がまったくない場合（手順 5）は、確からしさを付けない。代わりに、wiki がこの質問を扱っていないことと、取り込むとよいソースを伝える。

### 前提の出発点（どこに書かれていたか）

確からしさを決めるのは、前提が、その事柄の正本になる文章に書かれていたかである。世の中の事柄なら正本は元の資料で、wiki の中ではソースの要約ページと raw ソースがそれに当たる。wiki 自身の事柄（何をいつ取り込んだか、wiki の規約、ページの構成）なら、正本は wiki の記録そのものである。ページの frontmatter に `sources` があっても、そのページの個々の主張がそのソースから来たとはかぎらない。そのため、世の中の事柄は、ソースの要約ページか raw ソースの中で、その主張そのものを確かめたときだけ「高」にする。

表は上から順に見て、最初に当てはまった行の出発点にする。

| 前提が書かれていた場所 | 出発点 |
| --- | --- |
| wiki の外の知識（モデルの学習データ、一般的な知識）で補った | 低。回答の中でも、wiki の外の知識であることを明示する |
| 検索の抜粋（`snippet`）だけを見て、ファイルを読んでいない | 低 |
| wiki 自身の事柄を問う質問に、その記録（`log.md`、`SCHEMA.md`、インデックス、シンセシスのページを含むページの frontmatter）に書かれていることで答える | 高 |
| シンセシスのページ（`wiki/synthesis/`）にだけ書かれている | 下の「シンセシスのページ」に従う |
| 読んだソースの要約ページ（`wiki/sources/`）か raw ソースに、その主張が書かれている | 高 |
| 上のどれにも当たらない wiki のファイル（コンセプトやエンティティのページ、世の中の事柄を問う質問での `log.md` など）に書かれている。そのページに `sources` がない場合も含む | 中 |

前提がコンセプトかエンティティのページにあり、そのページの `sources` がソースの要約ページを挙げているときは、確からしさを決める前に、そのソースの要約ページを読んで前提を確かめる。読むだけで wiki は変わらないので、ユーザーの承認は要らない。確かめるのは結論の前提だけで、1 つの前提につき、インデックスの要約から前提に関係しそうなものを選んで 2 ページまでにする。2 ページで見つからないか、ページを読めなければ、出発点は「中」のままにし、「上げる方法」で raw ソースを読むことを提案する。

**シンセシスのページ。** シンセシスのページは、以前のクエリの回答を保存したものなので、根拠に数えない。シンセシスのページに書かれた主張は、その前提を、シンセシス以外のページか raw ソースで探して、ほかの結論と同じように決め直す。前提が見つからない主張は、wiki に根拠がないものとして「低」にする。シンセシスのページに書かれた確からしさは、そのときの wiki での判定なので、引き継がない。こうしておけば、回答を保存しても確からしさは変わらない。

### 結論の導き方

| 結論の導き方 | 結論の確からしさ |
| --- | --- |
| 前提をそのまま述べた、または言い換えただけで、新しい内容を足していない | その前提の確からしさ |
| 前提に書かれた値や事柄から、決まった手順で導いた（計算、数え上げ、並べ替え、書かれた値どうしの比較、数値や名前で書かれた条件に、書かれた値を当てはめること） | 使った前提のうちもっとも低い確からしさ。理由に、導いた手順を書く |
| 前提にない判断を加えて導いた（解釈、一般化、原因の推定、勧め、書かれていない条件への当てはめ、「安全な」「十分な」のような評価の言葉で書かれた条件への当てはめ） | 使った前提のうちもっとも低い確からしさと「中」のうち、低いほう |

前提が 1 ページにあるか複数のページにあるかは、導き方に関わらない。決まった手順で導いたのか判断を加えたのかで迷ったら、判断を加えたものとして扱う。

### 上限

| 当てはまること | 上限 |
| --- | --- |
| 根拠のページか段落が、仮説として書かれている（経験のパターンの `status: hypothesis`、「仮説の段階」などの記述）。根拠のグラフのエッジが `confidence: medium` か `status: proposed` | 中 |
| 根拠のグラフのエッジが `confidence: low` か `status: disputed` | 低 |
| その主張と矛盾する記述が、このクエリで読んだページ（別の wiki のページを含む）にあり、解決していない（手順 5 で矛盾をそのまま示す場合） | 低 |
| 質問が今のことを問うのに、根拠が `status: superseded` か `status: historical`、または置き換えられたと書かれた記述である | 低 |
| 質問の答えが時期や版で変わる（版、料金、設定、だれが担当しているか、など）のに、根拠に時期や版が書かれていないか、`log.md` やほかのページのより新しい記述と食い違う | 中 |
| インデックスから候補のページを見つけられず検索に頼り、その検索が意味の検索を wiki 全体には使っていなかった。検索の結果の `mode` が `hybrid` でないか、MCP の結果の `index.state` が `embedding` のときに当たる（以下「検索の縮退」） | 中 |

検索の縮退の理由は、下の表を上から順に見て、最初に当てはまった行にする。結果の `mode` と `index.state` は、意味の検索を使えたかどうかを表すだけで、理由は表さない（たとえば、埋め込みモデルを使えないときも、埋め込んでいないセクションがあれば `index.state` は `embedding` になる）。理由は、MCP なら `warning`、CLI なら付けた引数と標準エラーで決める。「上げる方法」は理由ごとに変わる。

| 順 | 理由 | 見分け方 |
| --- | --- | --- |
| 1 | ページ単位の検索にした | CLI に `--granularity page` を付けた。ページ単位の検索はいつも語彙検索である |
| 2 | 意味の検索を使わない指定をした | CLI に `--no-embed` を付けた |
| 3 | 埋め込みモデルを使えない | MCP の `warning` が「埋め込みモデルを使えない」で始まる。または CLI の標準エラーに「警告: ローカルの埋め込み検索を使えない」とある |
| 4 | 埋め込みの途中 | MCP の `warning` が「埋め込みモデルを用意している」か「索引を埋め込んでいる途中」で始まる。または `index.state` が `embedding` |
| 5 | 理由が分からない | 上のどれにも当たらない |

候補のページをインデックスから直接見つけた場合は、検索の縮退を上限に数えない。`--decide` の `failed_open: true` も上限に数えない。ふるい分けをしなかっただけで、結果は `--decide` を付けない検索と同じだからである。検索の `score`（RRF の値）と `--decide` の行ごとの判定の値は、検索の順位や関連の度合いであって回答の確からしさではないので、確からしさの根拠に使わない。

### 書き方

回答の最後に、次の形で書く。理由には、回答全体の確からしさを決めた前提の出発点、結論の導き方、当てはまった上限を、根拠のページの `[[wikilink]]` とともに書く。

```markdown
**確からしさ（confidence）: 中**

- 理由: 結論は [[消費税の軽減税率]] の記述をそのまま述べたものだが、そのページに `sources` がなく、ソースの要約ページでも raw ソースでも確かめられない。
- 上げる方法: 軽減税率の根拠になった資料（国税庁の通達など）を `/wiki:ingest` で取り込み、[[消費税の軽減税率]] の `sources` に結ぶ。取り込んだソースの要約ページで同じ記述を確かめられれば、「高」になる。
```

「高」のときは「上げる方法」を書かない。

### 確からしさを上げる方法を提案する

確からしさが「中」か「低」のときは、回答全体の確からしさを決めた要因（前提の出発点、結論の導き方、上限）ごとに、その要因を解消する方法を「上げる方法」としてユーザーに提案する。提案は具体的にし、取り込むとよい資料の種類、確かめるページ、使うコマンドを書く。要因と方法の対応は次のとおりである。

| 確からしさを決めた要因 | 提案する方法 |
| --- | --- |
| コンセプトかエンティティのページの `sources` がない | 元の資料を `/wiki:ingest` で取り込み、根拠のページの `sources` に結ぶ |
| ソースの要約ページに前提が見当たらない | raw ソースを読んで確かめる（下の段落）。raw にもなければ、前提を直接述べた資料を取り込む |
| シンセシスのページにしか書かれておらず、前提が見つからない | 前提を直接述べた資料を取り込む。シンセシスのページとして保存し直しても、確からしさは上がらない |
| 前提にない判断を加えて導いた | その結論を直接述べた資料を取り込む。シンセシスのページとして保存しても、確からしさは上がらない（自分の回答を根拠にすることになる） |
| 検索の抜粋だけを見た | 根拠のページを読んで答え直す。読むだけなので、エージェントがその場で行ってよい |
| wiki の外の知識で補った | その知識を裏づける資料を取り込む |
| 仮説として書かれている | 仮説を確かめた結果を `/wiki:learn` で記録する（経験のパターンを `supported` にできる証拠を残す）か、裏づける資料を取り込む |
| グラフのエッジの確からしさが低い、または議論が分かれている | エッジの `source` と `evidence` を確かめ、裏づける資料を取り込んでエッジを書き直す。`/wiki:graph lint` で証拠の欠落を確かめる |
| 読んだページの間で矛盾している | どちらが正しいかを決められる資料を取り込み、ユーザーが判断した結果をページに書く。ほかのページにも同じ矛盾がないかは、`/wiki:lint` に、その話題のページを挙げて確かめさせる（lint の内容の確かめは、エージェントが対象のページを絞って行う） |
| 置き換えられた記述にもとづいている、時期や版が書かれていない、新しい記述と食い違う | 時期や版の分かる最新の資料を取り込み、古いページを直す。古くなった主張がほかにもないかは、`/wiki:lint` に、その話題のページを挙げて確かめさせる |
| 検索の縮退（1. ページ単位の検索にした） | `--granularity page` を付けずに、MCP の `query` か `uv run --script` の形の CLI で、セクション単位で検索し直す |
| 検索の縮退（2. 意味の検索を使わない指定をした） | MCP の `query` か、`--no-embed` を付けない `uv run --script` の形の CLI で検索し直す |
| 検索の縮退（3. 埋め込みモデルを使えない） | `warning` か標準エラーの理由をユーザーに伝える。MCP なら `references/mcp-server.md` の「困ったとき」、CLI なら `references/retrieval-setup.md` に従って直してから検索し直す。待っても直らない |
| 検索の縮退（4. 埋め込みの途中） | 埋め込みが終わってから（`index.state` が `ready` になってから）同じ質問をし直す。待っても `ready` にならないときは、裏の埋め込みが失敗していることがあるので、`references/mcp-server.md` の「困ったとき」に従い `logs/server.log` を確かめる |
| 検索の縮退（5. 理由が分からない） | 意味の検索を使えなかったことをユーザーに伝え、MCP の `query` で検索し直すことを提案する |

raw ソースを読んで前提を確かめれば済む場合（ソースの要約ページはあるが、前提が要約に書かれていないか、言い回しが違うなど）は、「raw ソースを読んで確かめる」ことを提案する。raw は大きいことがあるので（手順 3）、ユーザーが承認したときだけ、エージェントがその場で読み、確かめた結果で確からしさを決め直す。raw を読んでも wiki は変わらない。

wiki を書き換える方法（取り込み、ページの修正、エッジの書き直し）は提案にとどめ、ユーザーの承認なしに実行してはならない。確からしさを上げるために、根拠のページを書き換えたり、主張を言い換えて強めたりしてはならない。

## 手順 6: 回答の保存を提案する

まとめた回答が新しいつながりを見いだすものである場合（wiki にまだない比較、複数のページの内容をまとめた分析、繰り返し出る質問への回答など）は、シンセシスのページとして保存することを提案する。ささいな回答ならユーザーは断り、中身のある回答なら受け入れるはずである。提案するのを基本とする。

確からしさが「低」の回答は、保存を提案しない。先に手順 5b の「上げる方法」を提案する。ユーザーが求めて保存するときは、本文に確からしさとその理由を残し、そのときの判定であることが分かるようにする。確からしさは frontmatter には書かない。wiki が変われば判定も変わるので、保存した値を後のクエリで使わないためである。

保存すると、次の frontmatter を持つ `wiki/synthesis/<answer-slug>.md` を作成する。

```yaml
---
type: "synthesis"
title: "回答の題名（質問か話題から付ける）"
question: "元の質問（そのまま、または軽く整えたもの）"
asked: 2026-04-15
sources: ["source-page-1", "source-page-2"]
sources_consulted: ["source-page-1", "concept-page", "entity-page"]
tags: ["..."]
created: 2026-04-15
updated: 2026-04-15
---
```

`type`、`title`、`tags`、`created`、`updated` は lint がすべてのページに求める必須項目で、`sources` は source 以外のページに求められる項目である。`sources` には回答の根拠にしたソースの要約ページ（`wiki/sources/`）のスラッグだけを入れ、`sources_consulted` には種類を問わず参照したページ（ソース、コンセプト、エンティティ、ほかのシンセシス）のスラッグを入れる。`question`、`asked`、`sources_consulted` はシンセシスのページだけの任意項目である。文字列の値は二重引用符で囲み、日付は囲まない。

比較や流れを答えた回答は、`page-conventions.md` の「図表」の形で、表や mermaid の図と説明を入れて保存する。

本文は、ユーザーに伝えた回答そのものである。wiki の文体に合わせて軽く手を入れてもよい。新しいシンセシスのページを、該当するインデックスに追加する。`log.md` には、`## [YYYY-MM-DD] query | <質問の要約>` の形の行を追記する（`## [2026-11-03] query | 軽減税率の対象の比較`）。操作名の `query` は英語のまま書き、説明は日本語で書く。

保存したシンセシスのページも、それ自体がクエリの対象になる。次にユーザーが近い質問をしたとき、そのシンセシスのページがもっとも関係の深い候補になるかもしれない。こうして調べた内容が積み重なっていく。

## 特殊なクエリの種類

**「トピック X について足りないものは？」**: X についての既存のページを読み、未解決の問いや、明示されていない前提を見つけ、取り込むとよいソースの候補を提案する。これは実質的に、トピックごとの小さな lint である。

**「X と Y を比べて」**: 両方のページを読み、`synthesis/` にすでに明示的な比較のページがないかを探し、比較表か対比の文章を作る。保存する候補として有力である。

**「X の時系列を見せて」**: `log.md` を使って、X に関係する取り込みの時系列を組み立て直し、関係するページの frontmatter の `created`/`updated` で補う。

**「ソース X は Y について何と言っている？」**: ソースの要約を見るために `wiki/sources/<x>.md` を読む。それで直接答えられなければ、`raw/<x>` を読む（大きければ分割して読む）。

**「この回答を lint でチェックして」**: 保存する前に、重要な主張の raw ソースを示して、ユーザーにその主張を検証してもらう。重要度の高い wiki（医療、法律、金融）では特に役立つ。

**「確からしさを上げるには？」**: 直前の回答の確からしさを決めた要因を手順 5b の表で示し、「上げる方法」を具体的に提案する。ユーザーが承認したものだけを行う。

## 避けるべきパターン

**念のために wiki のページを全部読む。** スケールせず、回答もあいまいになる。インデックスを信頼する。インデックスがうまく機能しないなら、迂回せずにインデックスを直す。

**確かな裏づけが必要な主張で、wiki だけを引用し、元のソースを引用しない。** wiki のページは言い換えである。ユーザーが検証する必要がありそうな主張では、引用を raw ソースまでたどれるようにする。

**ささいな回答を保存する。** すべての質疑応答が、残しておくページに値するわけではない。1行で調べがつく回答や、既存のページを言い直しただけの回答なら、synthesis/ を散らかさない。判断の基準は、「3か月後に似た質問をしたとき、これを見つけたいと思うか」である。

**wiki に情報がないのに、話をでっち上げる。** でっち上げた回答が信頼できる情報として保存されるより、「wiki はこれを扱っていない」と伝えるほうがよい。

**確からしさを印象で決める、または高めに付ける。** 確からしさは手順 5b の出発点と上限だけで決める。回答の書きぶりが自信ありげかどうか、ユーザーが望む答えかどうかで変えてはならない。迷ったら低いほうにする。
