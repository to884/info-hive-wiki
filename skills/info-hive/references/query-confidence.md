# 回答の確からしさ（confidence）の決め方

`/wiki:query` の回答の終わりに付ける確からしさの決め方と書き方の正本である。コマンドの手順 6b と、クエリのワークフロー（`query-workflow.md`）の手順 5b から、確からしさを書く前に読む。

回答の終わりに、回答の確からしさを「高」「中」「低」の 3 段階で示し、そう決めた理由を添える。確からしさは、wiki がその回答をどれだけ裏づけているかを表す。答えが世の中で正しい確率ではない。回答の正誤を確かめた評価のデータはないので、パーセントや 0.8 のような数値にしてはならない。

判定するのは、回答の結論（質問への答えそのもの）と、結論を導くのに使ったすべての前提である。結論が変わらない補足は判定しない。前提は結論が頼った主張で、wiki から取る。結論は前提をそのまま述べたものか、前提から導いたものである。

決め方は次の 3 段である。順番や読み手の印象で変わらないように、上げる方向の要因は設けない。

1. 前提ごとに、どこに書かれていたかで出発点を決める（「前提の出発点」）。
2. 前提ごとに上限を当て、出発点と上限のうち低いほうを、その前提の確からしさにする（「上限」）。
3. 結論の確からしさを、前提の確からしさと導き方で決める（「結論の導き方」）。結論にも上限を当てる。

回答全体の確からしさは、結論と前提のうちもっとも低いものにする。質問に複数の結論で答え、結論によって確からしさが違うときは、それぞれの結論のそばに「（確からしさ: 高）」「（確からしさ: 低）」のように書く。

wiki の外の知識は、前提に使わない。wiki の外の知識には、モデルの知識や一般的な知識のほか、会話に読み込まれたプロジェクトの指示（`AGENTS.md`、`CLAUDE.md` など）と、wiki の外のファイル（リポジトリの文書やコード）を含む。ただし、ソースの要約ページがそのソースの raw として指しているものは、wiki の raw の層なので外の知識に当たらない。指し方は次の 3 つである。frontmatter の `raw` が指す原本、frontmatter の `rag_job_id` のジョブが返す抽出済みの Markdown（rag の MCP の `job_status` で得る）、本文が raw として参照しているファイル（文字コードを変換した写しなど）。これらの raw がその本文で参照しているファイル（Web ページの raw が参照する `raw/assets/<スラッグ>/` の画像など）も含む。要約ページと関係なくリポジトリにあるだけのファイルは、これに当たらない。結論ごとに見て、前提を wiki から取れない結論は答えず、wiki がその部分を扱っていないことと、取り込むとよいソースを伝える（クエリのワークフローの手順 5）。どう探したかの説明と、取り込むとよいソースの提案には、自分で選んだ語を書かない。探した語は質問文にそのままある語だけを示し、ほかは「言い換えた語でも探した」と種類だけを書く。ソースは資料の種類と、質問文か wiki のページにある語で示す（クエリのワークフローの手順 5）。質問が複数の問いを含み、一部の問いにだけ wiki の答えがあるときも、答えのない問いを外の知識で埋めない。答えた結論にだけ確からしさを付け、扱っていない部分には付けない。wiki に関係する内容がまったくないときは、回答全体がこれに当たるので、確からしさを付けない。計算や比較などの決まった手順（「結論の導き方」）は知識ではないので、前提の値が wiki にあれば使ってよい。単位の換算（1 GiB は 1024 MiB）や暦の計算のように、定義で決まっている係数も手順に含める。使ったときは、理由に係数を書く。

## 前提の出発点（どこに書かれていたか）

確からしさを決めるのは、前提が、その事柄の正本になる文章に書かれていたかである。世の中の事柄なら正本は元の資料で、wiki の中ではソースの要約ページと raw ソースがそれに当たる。wiki 自身の事柄（何をいつ取り込んだか、wiki の規約、ページの構成）なら、正本は wiki の記録そのものである。ページの frontmatter に `sources` があっても、そのページの個々の主張がそのソースから来たとはかぎらない。そのため、世の中の事柄は、ソースの要約ページか raw ソースの中で、その主張そのものを確かめたときだけ「高」にする。ソースの要約ページに書かれていれば「高」で、raw ソースまで読む必要はない。

表は上から順に見て、最初に当てはまった行の出発点にする。

| 前提が書かれていた場所 | 出発点 |
| --- | --- |
| wiki の外の知識（モデルの学習データ、一般的な知識）でしか得られない | 前提に使わない。その前提が要る結論は答えず、wiki が扱っていないと伝える（上の段落） |
| 検索の抜粋（`snippet`）だけを見て、ファイルを読んでいない | 低 |
| wiki 自身の事柄を問う質問に、その記録（`log.md`、`SCHEMA.md`、インデックス、シンセシスのページを含むページの frontmatter）に書かれていることで答える | 高 |
| シンセシスのページ（`wiki/synthesis/`）にだけ書かれている | 下の「シンセシスのページ」に従う |
| 読んだソースの要約ページ（`wiki/sources/`）か raw ソースに、その主張が書かれている | 高 |
| 上のどれにも当たらない wiki のファイル（コンセプトやエンティティのページ、世の中の事柄を問う質問での `log.md` など）に書かれている。そのページに `sources` がない場合も含む | 中 |

前提がコンセプトかエンティティのページにあり、そのページの `sources` がソースの要約ページを挙げているときは、確からしさを決める前に、そのソースの要約ページを読んで前提を確かめる。読むだけで wiki は変わらないので、ユーザーの承認は要らない。確かめるのは結論の前提だけで、1 つの前提につき、インデックスの要約から前提に関係しそうなものを選んで 2 ページまでにする。2 ページで見つからないか、ページを読めなければ、出発点は「中」のままにし、「上げる方法」で raw ソースを読むことを提案する。

**シンセシスのページ。** シンセシスのページは、以前のクエリの回答を保存したものなので、根拠に数えない。シンセシスのページに書かれた主張は、その前提を、シンセシス以外のページか raw ソースで探して、ほかの結論と同じように決め直す。前提が見つからない主張は、wiki に根拠がないものとして答えず、wiki がその部分を扱っていないと伝える（上の「前提を wiki から取れない結論は答えない」と同じ）。シンセシスのページに書かれた確からしさは、そのときの wiki での判定なので、引き継がない。こうしておけば、回答を保存しても確からしさは変わらない。

## 結論の導き方

| 結論の導き方 | 結論の確からしさ |
| --- | --- |
| 前提をそのまま述べた、または言い換えただけで、新しい内容を足していない | その前提の確からしさ |
| 前提に書かれた値や事柄から、決まった手順で導いた（計算、数え上げ、並べ替え、書かれた値どうしの比較、数値や名前で書かれた条件に、書かれた値を当てはめること） | 使った前提のうちもっとも低い確からしさ。理由に、導いた手順を書く |
| 前提にない判断を加えて導いた（解釈、一般化、原因の推定、勧め、書かれていない条件への当てはめ、「安全な」「十分な」のような評価の言葉で書かれた条件への当てはめ） | 使った前提のうちもっとも低い確からしさと「中」のうち、低いほう |

前提が 1 ページにあるか複数のページにあるかは、導き方に関わらない。決まった手順で導いたのか判断を加えたのかで迷ったら、判断を加えたものとして扱う。

## 上限

上限は、下の表の行だけである。表にないことで確からしさを下げてはならない。観測や実行の回数、再現したかどうか、raw ソースを読んでいないこと、git の履歴やリポジトリのファイルで確かめていないことは、どれも上限にしない。当てはまる行が複数あれば、すべて当てて、もっとも低いものを取る。

| 当てはまること | 上限 |
| --- | --- |
| 根拠のページか段落が、仮説として書かれている（経験のパターンの `status: hypothesis`、「仮説の段階」などの記述）。根拠のグラフのエッジが `confidence: medium` か `status: proposed` | 中 |
| 根拠のグラフのエッジが `confidence: low` か `status: disputed` | 低 |
| その主張と矛盾する記述が、このクエリで読んだページ（別の wiki のページを含む）にあり、解決していない（クエリのワークフローの手順 5 で矛盾をそのまま示す場合） | 低 |
| 質問が今のことを問うのに、根拠が `status: superseded` か `status: historical`、または置き換えられたと書かれた記述である | 低 |
| 質問の答えが時期や版で変わる（版、料金、設定、だれが担当しているか、など）のに、根拠に時期や版が書かれていないか、`log.md` やほかのページのより新しい記述と食い違う | 中 |
| インデックスから候補のページを見つけられず検索に頼り、その検索が意味の検索を wiki 全体には使っていなかった。検索の結果の `mode` が `hybrid` でないか、MCP の結果の `index.state` が `embedding` のときに当たる（以下「検索の縮退」） | 中 |
| 前提が、YouTube の動画の raw、それを `raw` に持つ要約ページ、またはそれらを出典にするページに頼り、その raw の confidence が `medium` である（以下「動画のソース」）。confidence は、親の要約ページ（スラッグが raw のファイル名と同じページ）の `confidence` である。親の要約ページがなければ（raw を作って取り込みを止めたときなど）、raw の `caption_kind` から、`uploaded` なら `high`、`asr` なら `medium` とする | 中 |
| 動画のソースに頼り、その raw の confidence が `low` である | 低 |
| 前提の語が、`model` の訂正か留保の識別子（`〔訂正 L123-1〕`、`〔留保 L123-1〕`）に頼る。印の有無によらない。印のない語は、そのページの `## 字幕の訂正と留保` の定義（関係するページなら、印で指した要約ページの定義）の訂正した語か留保の語と照らして、識別子を引く | 低 |

検索の縮退の理由は、下の表を上から順に見て、最初に当てはまった行にする。結果の `mode` と `index.state` は、意味の検索を使えたかどうかを表すだけで、理由は表さない（たとえば、埋め込みモデルを使えないときも、埋め込んでいないセクションがあれば `index.state` は `embedding` になる）。理由は、MCP なら `warning`、CLI なら付けた引数と標準エラーで決める。「上げる方法」は理由ごとに変わる。

| 順 | 理由 | 見分け方 |
| --- | --- | --- |
| 1 | ページ単位の検索にした | CLI に `--granularity page` を付けた。ページ単位の検索はいつも語彙検索である |
| 2 | 意味の検索を使わない指定をした | CLI に `--no-embed` を付けた |
| 3 | 埋め込みモデルを使えない | MCP の `warning` が「埋め込みモデルを使えない」で始まる。または CLI の標準エラーに「警告: ローカルの埋め込み検索を使えない」とある |
| 4 | 埋め込みの途中 | MCP の `warning` が「埋め込みモデルを用意している」か「索引を埋め込んでいる途中」で始まる。または `index.state` が `embedding` |
| 5 | 理由が分からない | 上のどれにも当たらない |

候補のページをインデックスから直接見つけた場合は、検索の縮退を上限に数えない。`--decide` の `failed_open: true` も上限に数えない。ふるい分けをしなかっただけで、結果は `--decide` を付けない検索と同じだからである。検索の `score`（RRF の値）と `--decide` の行ごとの判定の値は、検索の順位や関連の度合いであって回答の確からしさではないので、確からしさの根拠に使わない。

## 書き方

回答の最後に、次の形で書く。1 行目は `**確からしさ（confidence）: 高**`、`**確からしさ（confidence）: 中**`、`**確からしさ（confidence）: 低**` のどれかを、この字句のまま書く。言い換えたり、見出しや表にしたりしない。あとで回答を集めて、機械で数えられるようにするためである。理由には、回答全体の確からしさを決めた前提の出発点、結論の導き方、当てはまった上限を、根拠のページの `[[wikilink]]` とともに書く。

```markdown
**確からしさ（confidence）: 中**

- 理由: 結論は [[消費税の軽減税率]] の記述をそのまま述べたものだが、そのページに `sources` がなく、ソースの要約ページでも raw ソースでも確かめられない。
- 上げる方法: 軽減税率の根拠になった資料（国税庁の通達など）を `/wiki:ingest` で取り込み、[[消費税の軽減税率]] の `sources` に結ぶ。取り込んだソースの要約ページで同じ記述を確かめられれば、「高」になる。
```

「高」のときは「上げる方法」を書かない。「原本を開くと確かめられる」のような、確かめ方の添え書きも書かない。

## 確からしさを上げる方法を提案する

確からしさが「中」か「低」のときは、回答全体の確からしさを決めた要因（前提の出発点、結論の導き方、上限）ごとに、その要因を解消する方法を「上げる方法」としてユーザーに提案する。提案は具体的にし、取り込むとよい資料の種類、確かめるページ、使うコマンドを書く。要因と方法の対応は次のとおりである。

| 確からしさを決めた要因 | 提案する方法 |
| --- | --- |
| コンセプトかエンティティのページの `sources` がない | 元の資料を `/wiki:ingest` で取り込み、根拠のページの `sources` に結ぶ |
| ソースの要約ページに前提が見当たらない | raw ソースを読んで確かめる（下の段落）。raw にもなければ、前提を直接述べた資料を取り込む |
| シンセシスのページにしか書かれておらず、前提が見つからない | 前提を直接述べた資料を取り込む。シンセシスのページとして保存し直しても、確からしさは上がらない |
| 前提にない判断を加えて導いた | その結論を直接述べた資料を取り込む。シンセシスのページとして保存しても、確からしさは上がらない（自分の回答を根拠にすることになる） |
| 検索の抜粋だけを見た | 根拠のページを読んで答え直す。読むだけなので、エージェントがその場で行ってよい |
| 質問の一部を wiki が扱っておらず、その部分に答えなかった | その部分を述べた資料を取り込む |
| 仮説として書かれている | 仮説を確かめた結果を `/wiki:learn` で記録する（経験のパターンを `supported` にできる証拠を残す）か、裏づける資料を取り込む |
| グラフのエッジの確からしさが低い、または議論が分かれている | エッジの `source` と `evidence` を確かめ、裏づける資料を取り込んでエッジを書き直す。`/wiki:graph lint` で証拠の欠落を確かめる |
| 読んだページの間で矛盾している | どちらが正しいかを決められる資料を取り込み、ユーザーが判断した結果をページに書く。ほかのページにも同じ矛盾がないかは、`/wiki:lint` に、その話題のページを挙げて確かめさせる（lint の内容の確かめは、エージェントが対象のページを絞って行う） |
| 置き換えられた記述にもとづいている、時期や版が書かれていない、新しい記述と食い違う | 時期や版の分かる最新の資料を取り込み、古いページを直す。古くなった主張がほかにもないかは、`/wiki:lint` に、その話題のページを挙げて確かめさせる |
| 動画のソースの confidence が `medium` か `low` | 同じ内容を述べた別の資料（投稿者の字幕のある版、講演の資料、記事、論文）を `/wiki:ingest` で取り込み、前提をその資料の要約ページで確かめる。訂正の根拠を `wiki_source:<スラッグ>` に替えられれば、疑いの重みが下がる。confidence は字幕の種類を出発点にするので、自動字幕のソースだけでは「高」にならない |
| `model` の訂正か留保に頼る | その語を逐語で含む資料（ほかのソース、動画の題名かチャプター）で根拠を確かめ、定義の根拠を `model` 以外に替える。ユーザーが字幕の語のほうが正しいと判断したら、定義と印を外す。どちらも wiki を書き換えるので、提案にとどめる |
| 検索の縮退（1. ページ単位の検索にした） | `--granularity page` を付けずに、MCP の `query` か `uv run --script` の形の CLI で、セクション単位で検索し直す |
| 検索の縮退（2. 意味の検索を使わない指定をした） | MCP の `query` か、`--no-embed` を付けない `uv run --script` の形の CLI で検索し直す |
| 検索の縮退（3. 埋め込みモデルを使えない） | `warning` か標準エラーの理由をユーザーに伝える。MCP なら `references/mcp-server.md` の「困ったとき」、CLI なら `references/retrieval-setup.md` に従って直してから検索し直す。待っても直らない |
| 検索の縮退（4. 埋め込みの途中） | 埋め込みが終わってから（`index.state` が `ready` になってから）同じ質問をし直す。待っても `ready` にならないときは、裏の埋め込みが失敗していることがあるので、`references/mcp-server.md` の「困ったとき」に従い `logs/server.log` を確かめる |
| 検索の縮退（5. 理由が分からない） | 意味の検索を使えなかったことをユーザーに伝え、MCP の `query` で検索し直すことを提案する |

raw ソースを読んで前提を確かめれば済む場合（ソースの要約ページはあるが、前提が要約に書かれていないか、言い回しが違うなど）は、「raw ソースを読んで確かめる」ことを提案する。raw は大きいことがあるので（クエリのワークフローの手順 3）、ユーザーが承認したときだけ、エージェントがその場で読み、確かめた結果で確からしさを決め直す。raw を読んでも wiki は変わらない。

wiki を書き換える方法（取り込み、ページの修正、エッジの書き直し）は提案にとどめ、ユーザーの承認なしに実行してはならない。確からしさを上げるために、根拠のページを書き換えたり、主張を言い換えて強めたりしてはならない。
