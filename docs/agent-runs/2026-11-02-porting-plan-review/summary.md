# llm-wiki-plugin 日本語移植計画レビューの総括

## 推奨

計画は方向性を維持したまま、実装に入る前に高重大度の 7 点（解析キャッシュの世代管理、検索の完了判定、P2 の基準測定、標準入力の UTF-8 化、D2 の空白除去の限定、コマンド名前空間の実測、Windows テストの POSIX 依存）を計画書に反映すること。作業の土台はエージェント D の高重大度 5 件を軸にし、エージェント A の実装・テスト側の抜け（評価ループの文字コード、偽バックエンド、CI、文書の整合）と、エージェント C の名前空間の指摘を合流させる構成を推奨する。

## 批評で動いたこと

- **エージェント A** は、自分が落としていた 3 件（P2 の JSON 解析エラー、標準入力、D2 の空白全削除の危険）を高に追加し、コマンド名前空間の自分の推測が公式仕様と合わないことを認めて P0 での実測を条件に加えた。MiniLM の「冒頭しか反映されない」も誤りの可能性が高いと訂正し、リリース数の自分の数え（9）も 14 に改めた。frontmatter の「、」区切りは自分の共通モジュール案を取り下げ、lint で指摘する案に乗り換えた。
- **エージェント B** は、高 3 件（キャッシュ、検索の完了判定、名前空間）の見落としを認め、公式文書を自分で取得して「`commands/wiki/query.md` は `/<plugin>:wiki:query`」を確認した。方針 C を「`/info-hive:*` に統一、P0 で実測」に変え、自分の順位を最下位に置いた。
- **エージェント C** は、Windows のテスト基盤、`wiki_evolve_loop.py:429` の文字コード不整合、偽バックエンドの ASCII 前提、設定ファイルの矛盾を追加し、解析キャッシュを中から高へ引き上げた。
- **エージェント D** は、Windows テストの移植を高優先度の作業として追加し、名前空間の指摘を中から強めた。方針 A は「独立コピーも可、履歴統合は必須でない」の立場を維持した。
- **最も鋭い反論**は 2 つ。1 つは C・D が出した「計画の直し方そのものが目的を達しない」系の指摘（D2 の空白全削除、`wiki_evolve.py` だけ直しても `grounded_verdict` は変わらない、`。` を文字クラスに足すだけでは空白なしの文を分割できない）で、A・B がそろって受け入れた。もう 1 つは C・D による「共通履歴がなくても cherry-pick はできる」で、A・B の方針 A の代案の根拠を弱めた。どちらも決定的で、後者は履歴取り込みを「必須」から「選択肢」に格下げさせた。

## 推奨案が残る理由

レビューで相互に確かめられた根拠を列挙する。行番号は作業ツリーのもの。

- **解析キャッシュ**（A 発見、B・C・D が確認）。`wiki_search.py:229-245` は sha256 が一致すると保存済みの `meta`・`links`・`sections` を再利用し、schema は `1` 固定。P1 の BOM・frontmatter 修正が既存 wiki に効かない。ただし C・D の訂正どおり、トークンは毎回再生成され、モデル変更時はベクトル索引が再構築される（`:447-461`）ので、問題は「旧解析結果の再利用」と「接頭辞・分割方式など入力文字列に現れない埋め込み設定の変更検出」の 2 つに分けて書く。
- **検索の完了判定**（A・C・D が独立に発見、B が確認）。`run_eval.py:213-227` の gate は方式間の相対比較のみで、hybrid は依存欠如時に省略される。加えて `wiki_search.py:729-732` は日本語クエリで JSON を出さず戻り、`run_eval.py:96` が無条件に `json.loads` するため、P2 の基準測定は「0 件」ではなく解析エラーで止まる（今回も確認済み）。
- **標準入力**（C・D 発見、A・B 確認）。`wiki_decide.py:640`、`wiki_evolve_agent.py:223`、`wiki_evolve_claude.py:44`、`wiki_evolve_api.py:130` が P1 の対象外。
- **D2 の空白全削除**（C・D 発見、A・B 確認）。`wiki_decide.py:358-365, 418-423` は引用一致でモデルを呼ばず `confidence=1.0` を返すため、`now here` と `nowhere` の同一視は誤った根拠の確定につながる。
- **コマンド名前空間**（C 発見、B が公式文書で確認、A・D が同意）。公式文書は `commands/db/migrate.md` を `/my-plugin:db:migrate` と記載。計画の「プラグイン名を変えても `/wiki:*` が残り衝突する」という前提は文書上成り立たない。ただし CLI 上の実測は 4 体とも未実施。
- **Windows テストの POSIX 依存**（A・B 発見、C・D 確認）。`test_adapters.py:71-106` の shebang・chmod・symlink と `test_evolution.py:148` の symlink は文字コードを直しても通らない。一方、B が挙げた `ps` は `os.name == 'posix'` で既に保護されており（今回確認済み）、障害には含めない。
- **設定ファイルの矛盾**（A・B・D 発見、C が追認）。`LLM_WIKI_CONFIG` と `~/.config/llm-wiki/remote.json` は `wiki_remote.py` と hosted 判定だけが使うため、方針 G で削ると方針 C の改名対象がなくなる。残るのはモデルキャッシュ `~/.cache/llm-wiki/fastembed`（`wiki_search.py:424-428`）。
- **評価ループの書き込み**（A 発見、C・D 確認）。`wiki_evolve_loop.py:429` は encoding 未指定で書き、直後に UTF-8 固定で読む。`:452, 458, 659` の `json.dumps` は `\uXXXX` を frontmatter に書き込み、手書き解析器は復号しない。ただし C の指摘どおり、新規生成される出典名は ASCII なので、発生条件（日本語パスの経路）を明記する。
- **事実の訂正で全員が収束した点**。リリース数は CHANGELOG 見出しで 14 本（2.0.0〜2.0.7 の 8 本と 3.0.0〜4.0.1 の 6 本、今回確認済み）。A の 9、B の 11 はともに誤り。SCHEMA の照合対象は「見出し 4 つと部分文字列 2 つ」。付録の行番号は v4.0.1 ではなく訳済み作業ツリーの値。構文木の同一性は docstring を除いた場合に限る。P0 の承認待ち 4 項目は 7 節（A・B・スキル名・docs）と食い違う。

## エージェントごとの要約

**エージェント A** は 25 件の最も網羅的な一覧を出し、解析キャッシュ、gate の相対比較、frontmatter の `\uXXXX` によるデータ破壊、`--help` が既に日本語で cp932 で落ちること、`package.json` が docs 専用、CHANGELOG と完了条件の衝突、JSON 出力キーの保護、偽バックエンドの ASCII 前提、英語評価セットの粒度など、他にない実装・テスト側の抜けを多く拾った。レビューで当たっていた指摘は、キャッシュの説明が広すぎること（トークンは再生成される）、recall の分母が 32 ではなく正例 27 であること、リリース数 9 の誤り、名前空間の未検証、標準入力・P2 の解析エラー・D2 の危険の見落とし、偽バックエンドに本番と同じトークン化を使う案が検証の独立性を弱めること。

**エージェント B** は fastembed の実物を uv キャッシュで確かめ（量子化版、0.22 GB、512 トークン切り詰め、e5 の接頭辞は自前）、Windows CI の POSIX 依存、cp1252 ランナーでは cp932 を再現できないこと、設定ファイルの所在、評価ループ ID の ASCII 制限、hosted テスト 5 件の漏れを正確に示した。レビューで当たっていた指摘は、キャッシュ・gate・標準入力・名前空間の見落とし、「共通履歴がないと cherry-pick できない」が誤りであること、評価ループ全体を Windows から外す案が要件の縮小であること、`ps` が既にガードされていること、`PYTHONIOENCODING=cp932` ではファイル入出力の既定を再現できないこと、リリース数 11 の誤り。

**エージェント C** は「計画どおり実装しても要件を満たせない箇所」に絞って高 4 件（検索の完了判定、名前空間、D2 の空白除去、標準入力）を挙げ、公式文書を根拠にした唯一の名前空間指摘、P2 の JSON 解析エラー、`grounded_verdict` の直接比較、句点分割の正規表現の限界を示した。確認済み・推論・未実測の区別が一貫している。レビューで当たっていた指摘は、Windows テスト基盤、偽バックエンド、`wiki_evolve_loop.py:429`、設定ファイルの矛盾の見落としと、計画の事実認定（構文木、件数、行番号の誤記）の照合が薄いこと。

**エージェント D** は C とほぼ同じ高 5 件を独立に確認し、さらにグラフの明示参照（`node_id`、`object`、`source`）が NFC 正規化から漏れている点、方針 C と G の矛盾、構文木の docstring 込み／除外の両比較、計画書の内部矛盾を行番号付きで示した。レビューで当たっていた指摘は、Windows テスト・偽バックエンド・評価ループの encoding 漏れの見落とし、名前空間を中に据えたこと、SCHEMA マーカーの呼称問題は現テンプレートで壊れていないので低でよいこと。

## 残るリスクと未確定事項

- **コマンド名の実測**。公式文書では `/info-hive:wiki:*` になる見込みだが、4 体とも CLI で確かめていない。選択肢は、(a) `commands/` を平らにして `/info-hive:*` に統一する（衝突リスクが消え、Q1 の決定は撤回）、(b) `/wiki:*` を維持する手段を P0 で検証してから確定する。(a) が単純で、B・C・D が推奨。
- **英語の劣化の許容幅**。gate は絶対値を見ないので、P2 で移植前の recall・MRR・偽陽性率を保存する必要がある。許容幅の数値は多言語モデルの実測前に決めるべきではない（C・D の留保）。英語だけの wiki 向けに bge-small-en を選べる設定を残すかも判断が要る。
- **Windows の完了条件の範囲**。(a) 評価ループのテストを Windows 対象外にする（B 案、要件の縮小）、(b) 偽コマンドの起動方法と symlink 検査を Windows 用に整備する（C・D 案、作業が増える）。計画 1 節が評価ループを対象に含めている以上、(a) を採るなら要件変更として明記する。
- **方針 A の形**。履歴ごと取り込む案（A・B）と独立コピー（C・D）はどちらも成立する。cherry-pick は upstream を fetch すれば履歴統合なしでも可能。決め手は `eval/evolution/workflows/build_suite.py` の扱いで、固定コミットを `git show` するこのツールを取り込まず UPSTREAM.md から参照するなら独立コピーで足りる。いずれでも、取り込んだ未コミット訳の差分かハッシュ一覧を先に保存する。
- **単漢字クエリ**。方針 E の bigram だけでは「税」「癌」が熟語に当たらない。漢字 unigram の併用（A・B 案）か、最小文字数の明示（C・D 案）か。前者が単純で検索品質への影響も小さい見込みだが、索引サイズは実測が要る。
- **frontmatter の「、」区切り**。4 体とも「受け付けずに lint で指摘」に収束。採用するならグラフ側の PyYAML と解釈をそろえる共通処理が必要。
- **D2 の正規化範囲**。英数字間の空白は保持し、日本語文字間の改行だけ吸収する。NFKC は引用原文との一致判定には使わない。負例を完了条件に加える。
- **MiniLM の実行時上限**。登録情報は 512 トークンだが、配布物の `tokenizer_config.json` と推論時の切り詰めは誰も実測していない。「日本語 200 文字」は固定値にせず P3 で測る。
- **評価ループの日本語保証範囲**。`grounded_verdict` と `wiki_evolve_loop.py` の生成文字列（英語の index・log 行、`Task:` などの本文）をどこまで初回に含めるか。含めないなら 1 節の「どれも正しく動く」から外して明記する。
