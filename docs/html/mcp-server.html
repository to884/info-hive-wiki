wiki の MCP サーバー

wiki プラグインには、検索用のローカル MCP サーバーがあります。埋め込みモデルの読み込み、埋め込み、索引の書き込みは、このサーバーだけが行います。wiki の Markdown は書き換えません。

コマンドの <skill-root> は、このスキルのディレクトリ（SKILL.md のあるディレクトリ）の実際のパスに置き換えます。書き方は SKILL.md の「スクリプトのパス」を参照してください。

コマンド（/wiki:query、/wiki:lint、/wiki:stats、/wiki:graph、/wiki:ingest のグラフの lint）は、まずこのサーバーのツールを使い、使えないときは CLI（wiki_search.py など）に戻ります。使い分けの規則は SKILL.md の「MCP のツールと CLI の使い分け」にあります。

仕組み

ホスト（Claude Code など）
  └─ 入口（wiki_mcp_launch.py、プラグインの設定で登録。依存を持たない）
        └─ stdio の中継（wiki_mcp_relay.py）
              └─ HTTP（127.0.0.1、トークン付き）
                   wiki の MCP サーバー（wiki_mcp_server.py、1 台に 1 つ）
                     ├─ 埋め込み: cl-nagoya/ruri-v3-130m（ONNX fp32、onnxruntime）
                     ├─ ベクトル索引: usearch（HNSW、f16、コサイン）
                     └─ 語彙検索: Tantivy の BM25（wiki の bigram のトークン）
  • ホストはセッションごとに入口を起動します。入口は中継の環境を確かめ。壊れていれば環境を入れ直してから、中継を起動します。中継は、動いているサーバーがあればそれを使い、なければ起動します。セッションがいくつあっても、サーバーは 1 つで、モデルも 1 回だけ読み込みます。
  • サーバーは中継から切り離して起動するので、セッションが終わっても残り、次のセッションが使います。要求がない状態が 15 分続くと、自分で止まります。次の呼び出しで中継が起動し直します。
  • サーバーは 127.0.0.1 だけで待ち受けます。起動時に作るトークンを Bearer 認証に使います。また、Host ヘッダーが 127.0.0.1:<ポート> でない要求を断ります。
  • サーバーの依存（約 1 GB）とモデル（約 530 MB）は、最初に使うときに取得します。最初の呼び出しは数分かかることがあります。
  • uv が依存パッケージをインストールしている途中でセッションが終わるなど、プロセスが停止すると、不完全な環境が残ることがあります。dist-info の METADATA が欠けると uv sync が失敗し、モジュールの本体だけが欠けると uv sync は成功するのに import に失敗します。そのため、次のようにします。
    • 入口は中継の環境を、中継はサーバーの環境を uv sync --script で確かめます。
    • 中継とサーバーは、起動の最初（標準入力を読む前）に、各パッケージの dist-info の RECORD（入れたファイルと大きさの一覧）と照らして欠けたファイルがないかを確かめ、主な依存を import します。壊れていれば終了コード 75 で止まり、起動した側（入口、中継）が環境を入れ直して、1 回だけ起動し直します。ファイルの大きさは site-packages のディレクトリの一覧（os.scandir）から読み、ファイルを 1 つずつ開きません。一覧で決められないファイル（Scripts/ の実行ファイル、シンボリックリンク、大文字と小文字の違う名前など）と、大きさが RECORD と違うファイルだけを 1 つずつ確かめ直します。Windows の一覧の大きさは、同じファイルを別のハードリンクから書き換えると古いまま残ることがあるが、uv は環境のファイルをその場で書き換えないので扱いません。
    • 入れ直しは、スクリプトごとのロック（uv のキャッシュの info-hive-locks/）を取ってから行います。ロックを取ったあとでもう一度確かめ、ほかのセッションが先に直していれば入れ直しません。

ツール

ツール 中身
query ハイブリッド検索（BM25 と埋め込みを RRF で融合）。結果の形は wiki_search.py --json と同じ
get_page 1 ページの frontmatter（日本語の別名のキーを英語にそろえたもの）と本文
list_index index.md の本文と indexes/ の一覧。name を渡すと indexes/ のそのファイル
lint 構造の lint（wiki_lint.py --json と同じ結果）と、オントロジーがあればグラフの lint（wiki_graph_lint.py --json）。検査結果を返します。ファイルは書き換えません。
stats 規模、構成、リンク密度の集計（wiki_stats.py --json と同じ結果）と、索引の状態とサーバーの版
graph グラフ（graph/graph.sqlite）への問い合わせ（wiki_graph_query.py --json と同じ結果）。DB は読み取り専用で開きます。
index_chunks rag などからチャンクを受け取り、wiki の外の索引に加える

リンクを読み飛ばしたときの通知（link_warnings）。 wiki の記事ファイルや、記事までのパスにリンクがある場合、どのツールもその記事を読みません。対象はシンボリックリンク、ジャンクション、名前の代理のリパースポイント、ハードリンクです（info-hive-dev の ADR-0029）。query、get_page、list_index、lint、stats、graph の結果には、読まなかったものを link_warnings（{"path", "kind"} の並び。なければ空）で必ず付けます。get_page と list_index の name で、リンクなので読まない記事を名前で引くと、「見つからない」ではなく「リンクなので読まない」のエラーを返します。

index_chunks 以外のツールには、wiki に wiki のルートの絶対パスを渡します。渡すのは初期化された wiki（ルートに SCHEMA.md がある）のルートです。SCHEMA.md のないディレクトリには、どのツールも「初期化された wiki ではない」のエラーを返し、索引も作りません。そのときは CLI でやり直さず、/wiki:init を提案します。lint、stats、graph は、同じ名前のスクリプトの関数をサーバーの中で呼びます。結果のキーも CLI の --json と同じ英語のままです。

query

引数 既定 説明
query （必須） 検索語。日本語は分かち書きせずに渡します。
wiki wiki のルート
top 10 返す行の数
type、tags、since frontmatter の type、タグ、更新日（YYYY-MM-DD）で絞り込む
per_page 2 1 ページから返すセクションの最大数
collection、query_tokens、docs、max_distance index_chunks で入れたチャンクを検索するとき（下を参照）

結果の index は、索引のセクションの数と埋め込み済みの数を示します。初回や大きな変更の直後は、埋め込みを裏で進めながら答えるので、state が embedding になり、warning に理由が入ります。そのあいだも語彙検索は wiki 全体を対象にします。

lint

引数 既定 説明
soft_cap、hard_cap 100、200 ページの大きさの上限の行数（--soft-cap、--hard-cap）
soft_char_cap、hard_char_cap 10000、25000 空白を除いた文字数の上限（--soft-char-cap、--hard-char-cap）。SCHEMA.md が別の値を決めている wiki では、その値を渡します。
required_fm type、title、tags、created、updated 必須の frontmatter のフィールドの配列
suggest_pages、suggest_min 偽、5 多くのページに出てくるのに専用のページがない語を挙げる
allowed_tags なし SCHEMA.md の「タグの体系」に並ぶタグの配列（--allowed-tags）。渡すと体系にないタグを unknown_tags に挙げます。省くか空にするとタグの検査をせず、summary.unknown_tags は null になります。
graph 真 グラフの lint も行う

結果の graph の state は次のどれかになります。

state 意味
checked findings に wiki_graph_lint.py --json と同じ結果が入る
disabled オントロジー（graph/ontology.yaml）がありません。message は CLI の 3 つの入口と同じ文面
error オントロジーを読めません。message に理由
skipped graph が偽

判定モデルを使う検査（wiki_graph_lint.py --decide）は含めません。

stats

結果には wiki_stats.py --json と同じ項目に加えて、次の 2 項目が入ります。

  • index: 索引のセクションの数（sections）、埋め込み済みの数（embedded）、残り（pending）、状態（ready、裏で埋め込み中の embedding、まだ埋め込みを始めていない pending）、置き場所（dir）、埋め込みモデル（model）
  • server: サーバーのコードの版（version）、プロトコルの版、pid

索引をまだ開いていない wiki では、索引を開いて変更を取り込みます。埋め込みは query を呼んだときに始まります。

graph

command 要る引数 中身
neighbors node 1 ホップ先のノード
edges subject、任意の predicate 主語から出るエッジ
path from_node、to_node、任意の max_depth（既定 6） 有向の最短経路
facts about 出るエッジと入るエッジ
  • ノード ID（concept:消費税 など）は NFC にそろえてから探します。
  • オントロジーがない wiki、graph.sqlite がない wiki、見つからないノードはエラーになります。DB は wiki_graph_extract.py が作ります。このツールは作りません。
  • グラフはナビゲーション用の索引です。重要な主張は、エッジの source が示すページで確かめてください。詳しくは references/graph-workflow.md を参照してください。

index_chunks

rag がチャンクを渡すためのツールです。wiki の Markdown は変えません。索引は collection ごとに分け、wiki の索引とは混ぜません。

引数 説明
collection 索引の名前。英小文字、数字、_、- の 1〜64 文字
tokenizer 語彙検索のトークンの作り方の名前（例: sudachi-c-normalized-v1）。collection を作ったときの値と違うと、処理は失敗します。
generation 世代。整数
chunks 各要素に id（collection の中で一意）、text、tokens（文字列の配列）、doc（文書の識別子）、任意の metadata、任意の vector か vector_b64（ruri-v3-130m の 512 次元。リトルエンディアンの float32 を base64 にしたもの）
delete_docs 丸ごと消す文書の識別子
reset 真なら collection を作り直す（tokenizer を変えるとき）
  • 語彙検索のトークンは呼び出し側が作ります。サーバーは分かち書きの辞書を持ちません。検索するときも、query に同じ作り方の query_tokens を渡します。
  • ベクトルがないチャンクは、サーバーが「検索文書: 」の接頭辞を付けて埋め込みます。
  • 渡したチャンクの doc ごとに、generation より古い世代の行を消します。同じ id を渡すと置き換えます。
  • 1 回の要求の本文は 64 MiB まで。ベクトルつきなら 1,000〜2,000 件ずつに分けて渡します。
  • 同じ id と generation で渡し直しても結果は変わりません。中継は、サーバーが呼び出しの途中で止まると、つなぎ直して同じ呼び出しを 1 回だけやり直します。

置き場所

OS 場所
Windows %LOCALAPPDATA%\info-hive\
macOS、Linux $XDG_DATA_HOME/info-hive/（未設定なら ~/.local/share/info-hive/）

その下に次を置きます。

  • server.json: 動いているサーバーのポート、トークン、pid、コードの版。中継だけが読みます。
  • index/<wiki のハッシュ>/: wiki ごとの索引。wiki のルートの絶対パスから作ります。ユーザースコープとプロジェクトスコープの wiki は別の索引になります。wiki の中の .wiki-cache/ には置きません。
  • index/collections/<名前>/: index_chunks の索引
  • models/: 埋め込みモデルのファイル（固定の revision から取得し、sha256 を確かめる）
  • logs/server.log: サーバーのログ

索引はいつでも削除できます。次に使うときに作り直します。大きな wiki では、再埋め込みに時間がかかることがあります。

環境変数

変数 説明
INFO_HIVE_DATA_DIR 置き場所を変える（検証用）
INFO_HIVE_MCP_IDLE_SECONDS 要求がなくなってから止まるまでの秒数（既定 900）
INFO_HIVE_EMBED_THREADS 埋め込みに使うスレッドの数（既定は onnxruntime の既定で、全コア）

MCP が使えないとき

サーバーの依存を取得できない、uv がない、などで MCP が使えないときは、今の CLI がそのまま使えます。

uv run --script "<skill-root>/scripts/wiki_search.py" "<検索語>" --wiki "<WIKI_ROOT>" --json
python "<skill-root>/scripts/wiki_search.py" "<検索語>" --wiki "<WIKI_ROOT>" --json --no-embed

CLI の埋め込み検索は、MCP のサーバーとは別のモデル（multilingual-e5-small）と別の索引（wiki の .wiki-cache/）を使います。

困ったとき

  • サーバーが起動しない: logs/server.log を見ます。uv run --script "<skill-root>/scripts/wiki_mcp_launch.py" --ensure を実行すると、サーバーを確かめ（なければ起動し）、トークンを除いた server.json の中身を表示します。

  • 社内ネットワークで起動しない（logs/launch.log か uv の出力に invalid peer certificate や UnknownIssuer がある）: TLS を検査するプロキシの CA を uv が信頼していません。入口と中継は UV_SYSTEM_CERTS=true（古い uv では UV_NATIVE_TLS=true）で 1 回だけやり直すが、CLI の uv run --script はやり直しません。環境変数 UV_SYSTEM_CERTS=true を設定するか、uv の uv.toml で system-certs = true を設定してください。設定後にホストを起動し直してください。Windows では組織の証明書を使う手順を参照できます。その場で CLI を動かすときは、uv run --system-certs --script ... のように --system-certs（古い uv では --native-tls）を付けます。

  • プラグインを更新した: 中継は server.json のコードの版を見て、古いサーバーを止めて起動し直します。

  • 「初期化された wiki ではない」のエラーになる: wiki に渡したディレクトリに SCHEMA.md がありません。wiki の場所が正しいかを確かめ、正しければ /wiki:init で初期化します。CLI も同じ判定で止まります。

  • uv の環境が壊れた（Failed to read metadata from installed package のような uv のエラーが出る）: 次の 2 つを実行して入れ直します。入口とサーバーは、起動のたびに同じことを自動で試します。

    uv sync --reinstall --script "<skill-root>/scripts/wiki_mcp_relay.py"
uv sync --reinstall --script "<skill-root>/scripts/wiki_mcp_server.py"

  • 直したのにツールが出ない: Claude Code は、接続に失敗した MCP サーバーを記録し、しばらく起動しないことがあります。記録は ~/.claude/mcp-needs-auth-cache.json の plugin:wiki:wiki に入ります。/mcp で wiki のサーバーをつなぎ直します。

  • Claude Code と Codex に wiki@info-hive プラグインを導入すると、MCP サーバー wiki が自動登録されます。

    スキル単体など、MCP を自動登録しない導入方法で MCP を使う場合は、ホストの MCP 設定に uv run --script "<skill-root>/scripts/wiki_mcp_launch.py" を stdio のサーバーとして登録します。<skill-root> は SKILL.md があるディレクトリの絶対パスに置き換えます。
