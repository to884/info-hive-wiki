移植計画

llm-wiki-plugin を日本語向けに移植する

praneybehl/llm-wiki-plugin は文書を訳しても日本語の wiki では動きません。検索のトークン化、埋め込みモデル、Windows の文字コードが英語前提だからです。この計画は、日本語に特化した移植版を info-hive リポジトリに作る手順をまとめたものです。

praneybehl/llm-wiki-plugin v4.0.1（コミット 2d24ccf、MIT ライセンス）
移植先
C:\Works\info-hive（現在は初回コミットの AGENTS.md のみ）

2026-11-02

2026-11-02 に質問 10 問の回答を受け、方針 C〜J は確定。方針 C（名前）は、コマンド名の実測結果を受けて同日に決め直した。4 モデルのレビュー（docs/agent-runs/2026-11-02-porting-plan-review/summary.md）の指摘を反映済み。方針 A・B と、見直しとレビューで加えた項目も同日に決定した（7 節）。未決の項目はない。P0〜P5 は完了した（4 節）。
01

目的と範囲

依頼の内容は次の 2 点です。

  • llm-wiki-plugin は日本語に対応していない。
  • 日本語に特化した移植版を info-hive リポジトリに作る。

ここでいう「対応」は、日本語のページ・クエリ・ファイル名で、取り込み、検索、lint、統計、グラフ、判定、評価ループがどれも正しく動くことを指します。文書やコメントの翻訳だけでは足りません。日英が混ざった wiki（技術用語は英語、本文は日本語）が普通にあると想定し、英語の扱いを悪くしないことも条件に含めます。

ホスト型 wiki（Cloudflare のサーバーと、それにつなぐ機能）は対象外です（Q4）。

02

調査で分かったこと

手元の llm-wiki-plugin の状態

  • C:\Works\llm-wiki-plugin（自分のフォーク）には、未コミットの日本語訳が 94 ファイル分あります。README、SKILL.md、コマンド 10 本、references 12 本、docs/ 全体、テンプレートの本文、Python のコメントと docstring が対象です。
  • Python は、docstring とコメントを除くと、訳の前後で構文木が同一でした。コード、正規表現、文字列リテラルは何も変わっていません。ただし docstring は argparse の説明に使われるので、--help の出力はすでに一部が日本語です（— を含み、cp932 の出力で落ちる）。
  • テンプレートの見出しと機械が読むキーは、意図して英語のまま残してあります。init_wiki.py --upgrade が ## Skill evolution などの見出しを行単位で照合するためで、この判断は正しいです。

日本語で何が起きるか

Python スクリプトと指示文書について、主な項目を影響の大きい順に並べます。行番号つきの一覧は 8 節 にあります。

主な問題
影響問題日本語での症状
壊れる 検索のトークン化が [a-z0-9]+ だけ 日本語だけのクエリはトークンが 0 個になり、「Empty query.」で終わる。埋め込み検索まで進まないので、ハイブリッド検索でも 0 件。日本語のページは BM25 の索引にほぼ何も載らない。
壊れる 埋め込みモデルが英語専用（bge-small-en-v1.5） 意味検索がほぼ雑音になる。類似度のしきい値（距離 0.35）も英語で調整した値。
壊れる Windows で文字コードを指定していない このマシンは cp932 が既定。日本語入りのテンプレートを read_text() すると UnicodeDecodeError。パイプ出力は文字化けし、— や 𠮷 を出力すると落ちる。評価ループが Node の CLI に渡す JSON も cp932 になる。
壊れる ファイル名とリンクの Unicode 正規化がない macOS の NFD ファイル名（ガイド.md など）が NFC のリンクと一致せず、リンク切れ・孤立ページ・重複スラッグとして誤検出される。
壊れる 解析キャッシュが古い解析結果を使い回す wiki_search.py は、ファイルの SHA-256 が同じなら保存済みの frontmatter・リンク・セクションを再利用する。キャッシュの形式番号は固定なので、P1 で BOM や frontmatter の解析を直しても既存の wiki には効かない。埋め込みの接頭辞や分割方式を変えても、索引のハッシュに現れないため作り直されない。
壊れる 評価が日本語のクエリで止まる 日本語のクエリで wiki_search.py が JSON を出さずに終わり、run_eval.py:96 の json.loads が失敗する。P2 の基準測定は「0 件」ではなくエラーになる。また --gate は方式どうしの相対比較しかしないので、英語の成績が全体に下がっても通る。
壊れる 評価ループが frontmatter を壊す wiki_evolve_loop.py は出典の一覧を ensure_ascii の既定のまま frontmatter に書く。日本語のパスは \uXXXX になり、手書きの解析器は元に戻さない。:429 は文字コードを指定せずに書き、直後に UTF-8 で読む。
壊れる 判定レイヤー D2 の文分割が [.!?] だけ 日本語の段落全体が 1 文になり、300 文字で切られる。行をまたぐ引用は空白の扱いの違いで一致しない。根拠のある関係が「根拠なし」と判定される。
劣化 語数とページの大きさを空白区切り・行数で数える 日本語の段落は 1 語と数えられる。改行しない段落は 800 行の上限をすり抜ける。
劣化 frontmatter の解析が ASCII 前提 全角の ： の行が捨てられる。[機械学習、深層学習] が 1 つのタグになる。ＡＩ と AI が別のタグになる。BOM 付きの UTF-8 は frontmatter なしと扱われる。
劣化 新規ページの提案が大文字始まりの英語句だけを拾う wiki_lint.py --suggest-pages が日本語の用語をひとつも提案しない。
劣化 Shift_JIS のソースと漢字の日付 Shift_JIS のファイルは黙って読み飛ばされる。2026年11月2日 は日付と認識されず、--since と更新停止チェックの対象から外れる。
劣化 判定モデルへの質問文が英語 日本語での精度は未検証。
見た目 出力の表示まわり 判定・lint・グラフの json.dumps が日本語を \uXXXX にする（検索の JSON 出力はすでに ensure_ascii=False）。全角文字で表の桁がずれる。出力メッセージの多くが英語。

変えてはいけないもの

次の文字列はスクリプトやテストが字句どおりに読むので、訳したり変えたりすると既存の wiki と互換がなくなります。このうち frontmatter のキーと、type・kind の値は、方針 B で日本語の別名も読めるようにします。書くときは英語のままです。

  • frontmatter のキー（type、title、tags、sources、created、updated など）と、type の値（source、entity、concept、synthesis）
  • グラフの述語名（mentions、sourced_from など）と kind の値。説明文は訳してよい。
  • SCHEMA.md のアップグレード検出用の目印 6 つ（行単位で照合する見出し 4 つと、部分文字列で照合する 2 つ）、固定のファイル名とディレクトリ名（index.md、log.md、raw/、graph/、.wiki-cache/ など）
  • 日付形式 YYYY-MM-DD と wikilink の書き方 [[slug|表示名]]
  • スクリプトの JSON 出力のキー（orphans、broken_links、results など）とコマンドラインの引数名。エージェントとテストが読む。

一方、ページの見出し（## Sources など）、ログ行の書式、スラッグの命名規則は、どのスクリプトも解析していないので自由に変えられます。

03

方針

どの方針も確定です。各項目の末尾に、根拠となった依頼または回答を示します。回答の一覧は 7 節 にあります。

確定

A. コピーして独立させ、v0.1.0 から始める

v4.0.1（2d24ccf）のファイルを履歴なしで取り込み、以後は移植元を追いかけずに独立して育てます。バージョンは v0.1.0 から始めます。移植元のスクリプト修正は、必要なものだけ移植元を git fetch して cherry-pick するか、手で移します。起点のコミットと取り込んだ修正は UPSTREAM.md に記録します。info-hive の修正を移植元に送ることはしません（Q9）。

eval/evolution/workflows/build_suite.py は移植元の固定コミットを git show で読むので、取り込まずに UPSTREAM.md から参照します。取り込む前に、未コミットの訳の差分（またはファイルごとのハッシュ）を保存します。

理由: 日本語訳がほぼすべての文書に、トークン化の変更がスクリプトとテストの基準データにまたがります。更新の速い移植元をマージで追うと、毎回大きな衝突が起きます。レビューでは履歴ごと取り込む案と 2 対 2 に分かれましたが、共通の履歴がなくても cherry-pick はできるので、コピーでも足ります。

根拠: 方針 A の質問への回答

B. 英語で書き、frontmatter のキーと type・kind の値は日本語でも読む

  • frontmatter のキーは、日本語の別名でも読めるようにする（例: タイトル → title、種類 → type、タグ → tags、出典 → sources、作成日 → created、更新日 → updated）。
  • type と kind の値も、日本語の別名で読めるようにする（例: 概念 → concept、人物 → person）。
  • スクリプト、テンプレート、エージェントが書くときは英語のキーと値を使う。日本語は読むだけにする。
  • グラフの述語名、--json の出力のキー、コマンドラインの引数名、SCHEMA.md の目印、固定のファイル名とディレクトリ名は英語のまま残す。
  • 別名の対応表は 1 か所に置き、検索・lint・統計の手書きの解析器と、グラフの PyYAML の両方が同じ表で英語に直す。同じページに title と タイトル のように両方がある場合は lint で指摘する。対応表は SCHEMA.md のテンプレートにも載せる。

理由: 人が日本語で書いたページを読めるようにしつつ、移植元の wiki や Obsidian のプラグインとの互換を保つためです。

根拠: 方針 B の質問と、範囲を確かめる追加の質問への回答

C. 名前: プラグイン名を wiki にし、コマンドを /wiki:query の形にする

  • プラグイン名は wiki にする。リポジトリ名とマーケットプレイス名は info-hive のままにする（導入時の指定は wiki@info-hive）。
  • commands/wiki/*.md を commands/*.md に移し、コマンドを /wiki:init、/wiki:query などにする。移植元の README や references にある /wiki:* の表記がそのまま正しくなる。
  • スキル名は info-hive のままにする（呼び出し名は wiki:info-hive）。
  • モデルのキャッシュは ~/.cache/info-hive/fastembed、環境変数は INFO_HIVE_* にする。移植元のキャッシュや設定を読んだり上書きしたりしない。

実測（Claude Code 2.1.316、2026-11-02）: 試験用のプラグインでは、commands/wiki/hello.md が /nstest:wiki:hello、commands/flat.md が /nstest:flat として登録された。短い形の /wiki:hello と /hello では起動しなかった。コマンド名には必ずプラグイン名が付くため、移植元のコマンドは実際には /llm-wiki:wiki:query であり、info-hive の /wiki:query とは衝突しない。

根拠: Q1 の再質問、追加の質問。最初の回答（プラグイン名 info-hive、コマンド /wiki:* を維持）は、実測で両立しないと分かったため決め直した。

D. スラッグに日本語を許す

ファイル名は 機械学習.md のように日本語で付けてよいとします。英語の固有名詞は英語のままでかまいません。比較の前にファイル名とリンク先を NFC に正規化します。

根拠: Q2

E. トークン化: NFKC → 小文字化 → ASCII の語 ＋ 日本語の文字 bigram

英数字は今までどおり語単位で、かな・漢字は 2 文字ずつ重ねて切り出します（1 文字だけの並びは 1 文字で）。形態素解析（SudachiPy など）は既定では使いません。P3 の評価で bigram より明らかに良ければ、入れたい人だけが使える任意の機能として追加します。

この定義だけでは、本文の「消費税」が「消費」「費税」になり、「税」「癌」のような単漢字のクエリが当たりません。そこで漢字は 1 文字単位（unigram）も索引に加え、文字種（漢字、ひらがな、カタカナ、英数字）の境界で区切ります。索引の大きさは P3 で測ります。

理由: 辞書が要らず、依存が増えません。trigram は「東京」「検索」のような 2 文字語に当たりません。

根拠: Q6、単漢字の質問への回答

F. 埋め込みモデル: 既定は 0.3 GB 程度まで

既定のモデルは 0.3 GB 程度に収まるものから、日本語の評価セットで選びます。大きいモデルは設定で選べるようにします。類似度のしきい値は、選んだモデルで測り直します。

  • 既定の第一候補: sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2（384 次元、約 0.22 GB）
  • 既定の候補（条件付き）: multilingual-e5-small。調査時点の fastembed 0.8.0 には含まれていないため、add_custom_model で登録する。サイズが 0.3 GB 程度に収まる形式がある場合だけ候補にする。
  • 設定で選べるモデル: intfloat/multilingual-e5-large（約 2.24 GB）など。英語専用の bge-small-en-v1.5 は残さず、多言語モデルだけにする。
  • e5 系を使うときは、クエリと文書に query: と passage: の接頭辞を付ける。

注意: paraphrase-multilingual-MiniLM-L12-v2 は、元のモデルの学習時の入力の上限が 128 トークンです。一方、fastembed の登録情報では 512 トークンで切り詰めます。実際にどこで切れるか、長い入力で精度が落ちるかは誰も測っていません。P3 で測り、埋め込み用にセクションを段落単位で分けるかを決めます。

根拠: Q3、英語専用モデルの質問への回答

G. ホスト型 wiki は提供せず、関連する機能を削る

server/ は取り込みません。サーバーがなければ使い道がないので、サーバーにつなぐ機能も合わせて削ります。

  • wiki_remote.py と eval/remote/
  • /wiki:migrate と /wiki:init --hosted
  • 各コマンドにある「ホスト型 wiki」の分岐（graph、ingest、lint、query、stats、upgrade）
  • references/hosted-mode.md と docs/hosted.md、他の references にあるホスト型の記述
  • wiki_decide.py の hosted バックエンド（wiki_remote を import している）
  • decision-questions.json をサーバー側の写しとバイト単位で比べるテストと CI の手順

理由: 保守の範囲が小さくなります。Python と TypeScript で同じ仕様を保つ必要もなくなります。

根拠: Q4。関連する機能まで削ることは、この回答からの解釈です。

H. 判定レイヤーと評価ループは両方残し、文字コードと D2 だけ先に直す

D2 の文分割（。！？ 対応）と空白の扱いは第 1 段階で直します。英語の質問文の日本語化と、判定モデルの日本語での精度検証は後回しにします。それまで判定レイヤーは既定で無効のままにします。

D2 は、根拠の引用が本文と一致するとモデルを呼ばずに確定させます（confidence=1.0）。このため、照合で空白をすべて除くと now here と nowhere を同じとみなし、誤った根拠を確定させます。吸収するのは日本語の文字どうしの間の改行と空白だけにし、英数字の間の空白は残します。NFKC は引用の一致判定には使いません。

評価ループは、初回リリースで文字コード、frontmatter の破損、引用の照合を直し、さらに評価ループが生成する文面（index と log の行、ページ本文の見出し、Task: などの項目名）も日本語にします。スクリプトが読み返す文字列は、読む側と同時に変えます。

根拠: Q7、評価ループの範囲の質問への回答

I. ページの大きさ: 目安 4,000 文字、上限 8,000 文字

空白を除いた文字数で数えます。移植元の行数の上限（目安 400 行、上限 800 行）も残し、どちらかを超えたら指摘します。値は実際の wiki を使いながら調整します。

根拠: Q5

J. 手元の訳を出発点にする

llm-wiki-plugin のフォークにある未コミットの訳を info-hive に取り込み、P5 で日本語の wiki の運用として書き直します。フォーク側の作業ツリーは、取り込みを確かめてから別ブランチに退避します。

根拠: Q8

    • 文字 bigram だけでは、日本語の負例 6 問のうち 5 問が何かに当たった（偽陽性率 0.833）。日本語のトークンを含むクエリでは、IDF で重みを付けたクエリの被覆率が 0.25 に満たないページを語彙検索の結果から外すようにした。負例の被覆率は最大 0.24 だった。被覆率はセクションではなくページで測る。セクションで測ると、長い言い換えのクエリ（j10）がどのセクションにも届かず、section が page を下回って --gate が落ちた。英数字だけのクエリには制限をかけない。
    • 埋め込みモデル: 第一候補だった paraphrase-multilingual-MiniLM-L12-v2（約 0.25 GB）は、埋め込みだけの recall@10 が日本語 0.340、英語 0.130（距離 0.3〜0.35）にとどまり、ハイブリッドでも語彙検索とほぼ同じだった。multilingual-e5-small（int8 版）は埋め込みだけで日本語 1.000、英語 0.963 だった。fastembed 0.8.0 は e5 系の接頭辞を自動では付けないので、query: と passage: を自分で付ける。
    • 重みとしきい値: 最初は int8 に量子化した版（約 0.14 GB）を使い、上限を 0.185 にした。正例の正解までの距離は日本語で最大 0.181、負例は最小 0.186 で、差が 0.005 しかなかった。CI では負例 1 問（j50、手元で 0.186）がこの上限を下回り、日本語のハイブリッドの偽陽性率が 0.167 になって --gate と --baseline が落ちた。MRR も Linux（0.961）と Windows（0.950）で違い、int8 の計算は CPU によって揺れることが分かった。fp16 の版（約 0.25 GB、0.3 GB の制限に収まる）に替えると、距離は int8 から 0.01 程度ずれ、正例の正解は日本語で最大 0.190、英語で最大 0.196、負例は日本語で最小 0.198、英語で最小 0.200 になった。0.190〜0.197 では成績が変わらないので、その中ほどの 0.193 にした。英語の recall@10 は int8 版の 0.963 から 0.926 に下がるが、P2 の基準と同じで、MRR は基準を上回る。セクションの埋め込みは int8 版の約 1.7 倍の時間がかかる（128 セクションで 9.4 秒）。評価セットが小さいので、しきい値は実際の wiki を使いながら見直す。
    • 入力の上限: e5-small の上限は 512 トークンで、評価セットのいちばん長いセクション（551 文字）でも 326 トークンだった。長いセクションのクエリ 3 問もすべて当たったので、段落単位の分割は入れない。
    • 漢字の unigram: 「税」を含む 8 ページのうち 4 ページは、「消費税」のような複合語の中にしか「税」がない。unigram がないと、単漢字のクエリはこれらに当たらない。日本語のコーパスで、トークン数は 7,627 から 11,247（47% 増）、異なり語数は 1,727 から 2,125（23% 増）になり、語彙検索 1 回の処理は 9 ms から 12 ms になった。ハイブリッドの MRR は bigram だけのとき 1.000 で、unigram を入れると 0.950 に下がる（int8 版で測った値。以下の比較も同じ）。クエリ側の unigram を 1 文字の漢字の並びだけに限ると MRR は 0.965 に戻るが、語彙検索の recall@10 が 0.972 から 0.929 に下がるので、方針 E のとおり索引とクエリの両方に入れた。
    • SudachiPy（0.7.0、sudachidict_core）: 語彙検索の recall@10 は A 単位 0.950、C 単位 0.922（被覆率の制限あり）、ハイブリッドの MRR は 0.961 と 0.947 で、bigram より明らかに良いとはいえず、処理は約 3 倍遅かった。任意の機能としても追加しない。
    • 検索時間: ハイブリッド検索 1 回の大半は fastembed の import（約 4 秒）とモデルの初期化（約 2〜5 秒）で、移植元の bge-small と比べて初回の初期化が約 1.3 秒長い程度だった。27 ページのコーパスで、embeddings.sqlite は約 1.7 MB、search-index.json は約 48 KB だった。

    • D2 の文分割を 。！？ にも対応させる。(?<=[。！？])\s* のように句点のあとに空白がなくても分ける（[.!?] の文字クラスに足すだけでは、空白のない日本語の文を分けられない）。照合は方針 H のとおり、日本語の文字どうしの間の改行と空白だけを吸収する。
    • 評価ループの照合を直す。wiki_evolve.py:260 の normalize は旧形式の採点にしか使われず、引用の照合は wiki_evolve_loop.py:73-79 の grounded_verdict が quote in source で直接比べている。両方を D2 と同じ規則にそろえる。
    • 評価ループが生成する文面（wiki_evolve_loop.py などが書く index と log の行、ページ本文の見出し、Task: などの項目名）を日本語にする。スクリプトやテストが読み返す文字列は、読む側も同時に変える。
    • 日付は ISO 形式（YYYY-MM-DD）を必須にし、それ以外は lint で指摘する。
    • Shift_JIS のソースは、取り込み時に検出して UTF-8 に変換する手順を用意する。
    • スクリプトの出力メッセージ、--help、lint の表示上の項目名を日本語にする。--json の出力のキーは英語のまま残す（方針 B）。全角文字を 2 桁と数えて表をそろえる。

    エージェント向けの指示を日本語の wiki に合わせて書き直す

    完了: 2026-11-03

    前提: P0 で取り込んだ訳（方針 D、I、J）。ページの大きさ、検索、評価ループの説明は P3・P4 の結果を待って確定する。

    • SKILL.md、コマンド 9 本、references、テンプレートを、訳文の直しではなく日本語の wiki の運用として書き直す。
    • スラッグの方針（日本語可、NFC）、ページの大きさ（文字数）、引用の書き方、ログ行の書式を日本語前提で書く。
    • SKILL.md の起動条件（description）を日本語の依頼で起動するように書き、スキル名を info-hive にする。
    • references に残る英語の例文（ingest-workflow.md の「as established in [[paper-X]]」など）を日本語の例に替える。
    • テンプレートの英語の見出しのうち、スクリプトが読む 6 つは残す。読まないもの（## Sources など）は日本語にしてよい。
    • オントロジーの述語の説明文を訳す（述語名は残す）。

    書き直しでは、次のように決めた。

    • スラッグ: 題名が日本語のページは日本語のスラッグ、英語の固有名詞や技術用語のページは英語のスラッグを基本にする。英字は小文字にしてハイフンでつなぐ。リンクの照合は大文字と小文字を区別するためである。空白、Windows でファイル名に使えない記号、wikilink の区切りになる記号、全角の「｜」「＃」、全角の英数字、半角のカタカナは使わない。どちらの言語の名前にするか迷う語の扱いは、wiki ごとに SCHEMA.md の「命名」の節で決める。
    • ページの大きさ: 「約 2,000 語」のような語数の目安はやめ、空白を除いた文字数と行数で書く。大きいソースを分割して読む目安は「約 1 万文字（英語なら約 5,000 語）」にした。
    • 引用: 本文では「」で囲む。グラフの evidence と、判定・評価ループの根拠はソースの文をそのまま写す。照合の規則（日本語の文字どうしの間の改行は吸収し、全角と半角の違いは吸収しない）を文書に書いた。
    • ログ行: ## [YYYY-MM-DD] <操作名> | <説明> の操作名は英語のまま、説明とサブ行（ グラフ: ノード +N、型付きエッジ +M）は日本語にした。評価ループが書く - YYYY-MM-DD: … の行は変えていない。
    • 見出し: SCHEMA.md.template は目印の 4 つの見出しだけ英語で残し、ほかは日本語にした。index.md・log.md・page.md・pattern.md などのテンプレートの見出しはすべて日本語にした。評価ループが index.md と log.md を新しく作るときの見出しも、テンプレートに合わせて wiki_evolve_loop.py で変えた。
    • 例: グラフの例は、移植元の実在の人物と会社から、架空の日本語の例（person:山田太郎、company:やまだ製作所）に替えた。日本語のスラッグを含むノード ID で、グラフの lint、抽出、クエリが動くことを確かめた。
    • /wiki:upgrade: 移植元の llm-wiki で作った wiki から移るときの注意点（埋め込みの索引とパースキャッシュの作り直し、モデルのキャッシュの場所、環境変数の改名、ホスト型 wiki がないこと）を書いた。
    • 英語のまま残したもの: 判定モデルに渡す質問（decision-questions.json）と、評価ループのランナーに渡すプロンプト（方針 H）。decision-models.md に、日本語での精度は確かめていないと書いた。
    • 利用者向けの README.md と docs/ にも、古い埋め込みモデル名、行数だけの上限、英小文字だけのファイル名の記述が残っていたので、合わせて直した。

05

完了の判定

初回リリースまでを終えたと判断する条件です。検索の数値の目標は P2 で基準を測ってから決めます。

  • Windows（cp932 が既定、PYTHONUTF8 なし）で、すべてのスクリプトが日本語・—・𠮷 を含む入出力（標準入力を含む）で落ちず、文字化けしない。
  • 日本語だけのクエリが結果を返し、日本語の評価セットで P2 の基準を上回る。「税」のような単漢字のクエリが「消費税」を含むページに当たる。
  • frontmatter のキーと type・kind の値を日本語で書いたページを、英語で書いたページと同じように検索・lint・統計・グラフで扱える。スクリプトとテンプレートが書くページは英語のキーと値になっている。
  • 移植前に作った既存の wiki で、P1 以降の解析の修正が効く（古い解析キャッシュが自動で作り直される）。
  • 既定の埋め込みモデルのダウンロードが 0.3 GB 程度に収まる。
  • 英語の評価セットの --gate が通り、P2 で保存した絶対値からの低下が、P3 で決めた許容幅に収まる。
  • 日本語のファイル名のページ、NFD のファイル名のページに NFC のリンクを張っても、リンク切れや孤立ページとして報告されない。
  • 8,000 文字を超えるページが、行数に関係なく lint で指摘される。
  • 移植元の llm-wiki で作った既存の wiki を、変換なしで lint・検索できる。
  • 導入後、/wiki:init などの 9 本のコマンドが /wiki:* の形で起動する。移植元と同時に入れても、コマンド、モデルのキャッシュ、環境変数が衝突しない。
  • D2 のテストで、。 区切りの段落の後半にある根拠と、行をまたぐ引用が見つかる。空白の有無で意味が変わる負例は一致しない。
  • 評価ループが書いた frontmatter に、日本語のパスが \uXXXX のまま残らない。評価ループが生成する index と log の行、ページ本文が日本語になっている。
  • ホスト型 wiki への参照（wiki_remote、--hosted、/wiki:migrate）が、CHANGELOG.md と UPSTREAM.md を除くコードと文書に残っていない。
  • CI が Linux と Windows の両方で通る。評価ループのテストも Windows で動く。
06

リスク

リスク起きること対策
小さい多言語モデルの精度が足りない 0.3 GB 程度のモデルでは、日本語の意味検索が期待ほど良くならない。 P3 で bigram の語彙検索だけの成績とも比べる。足りなければ、大きいモデルを設定で選ぶよう README で案内する。
英語の検索の成績が下がる 英語専用モデルを残さないので、英語だけの wiki でも多言語モデルを使う。英語の意味検索は、今の bge-small-en-v1.5 より弱くなるおそれがある。 P2 で英語の絶対値を保存し、P3 で比べる。下がり幅を CHANGELOG と README に書く。
埋め込みの入力上限 MiniLM 系は元の学習時の上限が 128 トークンで、長いセクションでは精度が落ちるおそれがある。fastembed の切り詰めは 512 トークンで、実際の影響は未測定。 P2 の評価セットに長いセクションを入れ、P3 で段落単位の分割と比べる。
Windows の CI で不具合が再現しない GitHub の Windows ランナーは cp1252 と見込まれ、UTF-8 の日本語をほぼ例外なく読めてしまう。encoding の付け忘れが CI を通り抜ける。 CI で cp932 を固定するか、encoding の付け忘れを静的に検査する（P0）。
bigram で索引が大きくなる 日本語のページはトークン数が文字数とほぼ同じになり、キャッシュと BM25 の計算が重くなる。 P3 で索引の大きさと検索時間を測る。問題があれば形態素解析と比べる。
プラグイン名 wiki が他と重なる 同じく wiki という名前のプラグインを入れると、コマンドとスキルの名前がぶつかる。移植元（llm-wiki）とは衝突しない。 README に、wiki という名前のプラグインとは併用できないと書く。マーケットプレイス名 info-hive で出どころを区別する。
移植元の修正を取り込めなくなる 独立させるので、移植元のバグ修正が自動では入らない。 UPSTREAM.md に起点を記録し、移植元のリリースごとに差分を見て必要なものを個別に取り込む。
判定モデルが日本語で弱い 判定レイヤーを有効にすると、関係のある結果を誤って捨てる。 精度を検証するまで判定レイヤーは既定で無効にする（方針 H）。
ホスト型 wiki の削り残し 文書やコマンドに --hosted などの記述が残り、エージェントが存在しない機能を案内する。 P0 の最後に参照を検索して確かめる。完了の判定にも入れてある。
